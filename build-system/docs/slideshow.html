The Problem

Monolithic RootFS Rebuilds

Today, a one-line app change forces a full rootfs.ext4 rebuild. Every byte is redistributed even when most haven't changed.

A rootfs is really four independent concerns:

3 App code changes every deploy
2 Heavy deps changes independently
1 Platform binaries changes occasionally
0 Base OS changes ~monthly

A monolithic blob conflates all four:

  • No way to skip unchanged work
  • No sharing of common layers across workloads
  • No way to know which bytes actually changed
  • Full rebuild + full redistribute on every deploy

Layer Model

Build Once, Reuse Forever

When only the app code changes, only that layer is re-charged. Everything below it is pulled from The Reserve.

The Alloy

Dockerfile as Build Spec

A standard multi-stage Dockerfile with Steel label annotations. Works with docker build for local dev and with The Smelter for production.

FROM debian:bookworm-slim AS base_os LABEL steel.layer="base-os" LABEL steel.layer.order="0" RUN apt-get update && apt-get install -y ca-certificates curl FROM base_os AS platform LABEL steel.layer="platform" LABEL steel.layer.order="1" COPY steel-init /usr/local/bin/steel-init FROM platform AS chrome LABEL steel.layer="chrome" LABEL steel.layer.order="2" RUN apt-get install -y chromium FROM chrome AS app LABEL steel.layer="app" LABEL steel.layer.order="3" COPY steel-browser-server /usr/local/bin/ FROM scratch AS steel_release LABEL steel.release="true" LABEL steel.release.layers="base-os,platform,chrome,app" LABEL steel.meta.vcpus="4" LABEL steel.meta.memory_mb="4096"

Deploy Path

From Reserve to Running VM

Microvisor only imports the top layer — it contains the complete rootfs. Lower layers exist for caching and diffing.

Key properties

  • Layer import is a one-time cost per layer per host
  • Subsequent VM launches snapshot the existing thin volume
  • Integrity verified before writing to thin pool
  • Hash mismatch → reject, abort deploy
  • Tags enable promotion: staging → production

Why store all layers?

  • Cache: skip rebuilding unchanged layers
  • Diff: see which component changed between releases
  • Sharing: multiple workloads share base layers

Security

Build, Store, Deploy

Isolated Builds
BuildKit executes each RUN in a restricted container. The Smelter never executes Dockerfile instructions directly.
Supply Chain Pinning
FROM references resolve to registry digests, not mutable tags. Base image updates change the input hash and trigger rebuilds.
Append-Only Store
Published layers are immutable. Different content under an existing hash is rejected. Corruption detected by verify_store scans.
Consumer-Side Verification
Microvisor verifies SHA-256 of decompressed bytes against the manifest before writing to thin pool. No trust delegation.
Build Provenance
Every layer records: builder version, timestamp, build host, input manifest hash, parent hash, stage definition hash.
Hash Chain Integrity
Each layer records its parent's hash. A change to any lower layer invalidates everything above it. No stale references possible.

Core Invariants

  • Idempotent: same spec + same inputs = same content addresses, every time
  • Content-addressed: identity from cryptographic hash, not names or timestamps
  • Append-only: published layers are immutable; deletion only via explicit GC
