# Product Requirements Document (PRD): Microvisor Build System

## 1. Product Objective
To provide a layered, content-addressed build system that produces rootfs artifacts for Microvisor's Firecracker microVMs. The build system must make each logical component of a rootfs (base OS, platform, dependencies, application) independently buildable, cacheable, and diffable — so that a one-line app change never forces a full rootfs rebuild.

**Concrete performance targets** (subject to revision once benched):
- Layer cache-hit decision (hash lookup against store): **< 5 ms**
- Incremental rebuild (single top-layer change, all lower layers cached): **< 30 s** for a typical Steel workload
- Full rebuild (cold, no cache): **< 5 min** for a 4-layer Steel browser workload
- Build diff (two manifests): **< 100 ms**
- Store publish (single layer): bounded by disk I/O, not system overhead — **< 1 s** of non-I/O overhead per layer

**Core invariants:**
- Builds are **idempotent**. Running the same build spec against the same inputs produces the same content addresses and artifacts every time.
- Layers are **content-addressed**. Identity is derived from a cryptographic hash of inputs, not from names, timestamps, or sequence numbers.
- The store is **append-only at the layer level**. A published layer is immutable. Deletion happens only through explicit garbage collection of unreferenced layers.

## 2. Target Audience
**Platform Engineers & Build Operators:** Individuals responsible for producing, versioning, and deploying rootfs images for Steel workloads on the Microvisor. They need fast incremental builds, the ability to audit exactly what changed between releases, and confidence that artifacts haven't been tampered with.

## 3. Core Features & Operator Stories

### Feature 0: Dockerfile-Driven Build Specification
The build system consumes a standard multi-stage Dockerfile as its build spec. Each Dockerfile stage annotated with Steel labels maps to a layer in the build system. This means the same Dockerfile works with plain `docker build && docker run` for local development and with the build system for production layer extraction.

*   **Operator Story (Local Testing):** "As a developer, I need to `docker build` and `docker run` the same Dockerfile that the build system consumes, so that I can test locally without custom tooling."
*   **Operator Story (Declare a Release):** "As a build operator, I need to declare the complete layer stack for a release in a single Dockerfile, so that the build is fully reproducible from that file alone."
*   **Operator Story (Flexible Layer Types):** "As a platform engineer, I need to define layers for different concerns — base OS, platform tooling, heavy dependencies, application code — using standard Dockerfile multi-stage builds, without the build system imposing a fixed layer taxonomy."
*   **Operator Story (Composability):** "As a build operator managing multiple workload types, I need to reuse the same base OS and platform stages across different Dockerfiles, so that shared infrastructure is defined once and built once."
*   **Feature Details:**
    *   **Multi-Stage Dockerfile as Spec:** Each `FROM ... AS <stage_name>` block in the Dockerfile is a candidate layer. The build system parses the Dockerfile, identifies annotated stages, and maps them to the layer stack.
    *   **Steel Labels for Annotation:** Stages are annotated with `LABEL` directives to provide metadata the build system can parse. Labels declare layer name, ordering, and release membership. Example: `LABEL steel.layer="base-os"`, `LABEL steel.layer.order="0"`.
    *   **`steel_release` Stage (Required):** The Dockerfile must include a stage labeled `LABEL steel.release="true"` that declares the ordered layer list (e.g., `LABEL steel.release.layers="base-os,platform,chrome,app"`). This stage is the build's entry point and produces the release manifest.
    *   **Stage Inputs and Hashing:** The build system hashes the full stage definition (Dockerfile instructions for that stage + parent layer hash) to compute the content address. Standard Dockerfile instructions (`RUN`, `COPY`, `ADD`, `ENV`, etc.) are all supported — Docker/BuildKit handles execution.

### Feature 1: Content-Addressed Layer Builder
The builder parses the Dockerfile, identifies Steel-annotated stages, and produces content-addressed layer artifacts. Docker/BuildKit is the execution engine — the build system orchestrates it, extracts per-stage results, and computes stage-level content addresses for the store.

*   **Operator Story (Incremental Builds):** "As a build operator, I need the build system to skip layers whose inputs haven't changed, so that deploying a one-line app change takes seconds, not minutes."
*   **Operator Story (Idempotency):** "As a platform engineer, I need repeated builds of the same spec to produce identical artifacts, so that I can verify a build without worrying about non-determinism."
*   **Operator Story (Cache Reuse):** "As a build operator, I need the builder to check the store for an existing layer before building, so that cross-workload shared layers (like the base OS) are never rebuilt unnecessarily."
*   **Operator Story (Build Isolation):** "As a security engineer, I need each layer build to execute in an isolated container, so that a compromised build step in one layer cannot tamper with another layer's artifacts."
*   **Feature Details:**
    *   **Docker/BuildKit as Execution Engine:** The build system delegates stage execution to Docker/BuildKit, inheriting its per-instruction caching, container isolation, and multi-stage build support. The build system's role is orchestration, layer extraction, and content addressing — not reimplementing a container build engine.
    *   **Hash-Before-Build:** Before executing a stage, the builder computes the expected content address (hash of parent layer hash + stage definition hash). If the store already contains a layer with that address, the build is skipped entirely — Docker is never invoked for that stage.
    *   **Layer Extraction:** After Docker/BuildKit completes a stage, the build system extracts the stage's filesystem output and converts it to the appropriate layer format for the store (format depends on TAD layer format decision).
    *   **Layer Chain Integrity:** Each layer records its parent's content address. If a lower layer is rebuilt (because its inputs changed), all layers above it in the stack are invalidated and rebuilt. This is enforced by the content-address chain, not by manual dependency tracking.

### Feature 2: Layer Store (External Dependency: `fs-storage`)
The store is a separate module (`fs-storage`) that provides persistent, content-addressed storage for layer artifacts and build metadata. The build system publishes to and pulls from the store via its API. See the `fs-storage` PRD for full requirements.

*   **Build System's Relationship to the Store:**
    *   **Publish after build:** When the builder completes a stage, it publishes the layer artifact + metadata to `fs-storage`.
    *   **Check before build:** Before executing a stage, the builder queries `fs-storage` to see if a layer with the expected content address already exists. If so, the build is skipped.
    *   **Assemble release manifest:** On build completion, the builder publishes the release manifest (referencing layers by content address) to `fs-storage`.
    *   **Diff via store:** Build diffing (Feature 3) reads two release manifests from `fs-storage` and compares their layer stacks.

### Feature 3: Build Diffing
The diff engine compares two builds at the manifest level, showing exactly which layers changed, were added, or were removed.

*   **Operator Story (Release Comparison):** "As a platform engineer, I need to diff two releases and see exactly which layers changed, so that I can assess the blast radius of a deploy before pushing it."
*   **Operator Story (Regression Triage):** "As an SRE triaging a regression, I need to see which layer introduced a change between a known-good and known-bad release, so that I can narrow the investigation to the right component."
*   **Operator Story (Change Auditing):** "As a security engineer reviewing a release, I need to verify that only the expected layers changed and that all unchanged layers have the same content addresses as the previous release."
*   **Feature Details:**
    *   **Manifest-Level Diff:** Compares the ordered layer lists of two release manifests. For each layer position: unchanged (same hash), modified (different hash), added, or removed.
    *   **Layer-Level Diff (Stretch):** For modified layers, optionally inspect file-level changes within the layer delta. **POC:** manifest-level diff only. **Trigger to add layer-level diff:** when manifest-level diff is insufficient for triage (operators regularly need to know *which files* changed within a layer, not just *that* the layer changed).

### Feature 4: Security & Provenance
Every artifact the build system produces must be verifiable — its content, its origin, and its integrity.

*   **Operator Story (Integrity Verification):** "As a deploy operator pulling a layer, I need to verify that the layer's content matches its claimed hash before using it, so that a corrupted or tampered artifact never reaches a running VM."
*   **Operator Story (Provenance Tracking):** "As a security auditor, I need to know who built a layer, when, from what inputs, and on what machine, so that I can trace any artifact back to its origin."
*   **Operator Story (Immutability):** "As a platform engineer, I need the guarantee that a published layer cannot be silently overwritten, so that a content address always refers to the same bytes."
*   **Operator Story (Supply Chain):** "As a security engineer, I need the build system to record the full input chain for each layer (parent hash, stage definition, external artifact references), so that I can audit the supply chain for any release."
*   **Feature Details:**
    *   **Cryptographic Content Addressing:** Layer identity is a SHA-256 hash (or equivalent) of the layer's content. This hash is verified on every pull from the store.
    *   **Build Provenance Metadata:** Each layer's metadata includes: builder version, build timestamp, build host identifier, input manifest hash, parent layer hash, stage definition hash. This metadata is stored alongside the layer in the store.
    *   **Append-Only Layer Semantics:** Once a layer is published to the store, its content is immutable. Re-publishing the same content address is idempotent (no-op). Publishing different content under an existing address is rejected (hash collision or tampering).
    *   **Manifest Signing (Deferred):** Cryptographic signing of release manifests to attest that a specific build operator produced a specific release. **Trigger to implement:** when releases are consumed by hosts the build operator doesn't directly control, or when compliance requirements mandate signed artifacts.

### Feature 5: API Interface
All build system operations are exposed through a programmatic API. The CLI is a thin client built on top of this API.

*   **Operator Story (Automation):** "As a CI/CD engineer, I need to trigger builds, publish layers, pull artifacts, and diff releases programmatically, so that the build system integrates into automated pipelines without CLI scraping."
*   **Operator Story (CLI):** "As a build operator working interactively, I need a CLI that exposes every API operation with clear inputs and outputs, so that I can build, inspect, and debug without writing scripts."
*   **Operator Story (Extensibility):** "As a platform engineer, I need the API to be the single source of truth for all operations, so that future integrations (webhooks, dashboards, Microvisor direct integration) compose on the same interface."
*   **Feature Details:**
    *   **API-First Design:** Every operation (build, publish, pull, diff, list, GC) is an API call. The CLI is a consumer of the API, not a separate code path.
    *   **Build Operations:** `build` (execute a Dockerfile, return release manifest), `build-status` (query in-progress or completed builds).
    *   **Store Operations:** `publish` (push layer + metadata to store), `pull` (retrieve layer by content address and format), `list` (query builds/layers), `gc` (identify/remove unreferenced layers).
    *   **Tag Operations:** `tag` (create or update a named tag pointing to a release manifest), `untag` (remove a tag), `list-tags` (list all tags and their manifest hashes), `resolve-tag` (resolve a tag name to a manifest hash). Tags are mutable pointers — `production`, `staging`, `canary` — that give stable names to promoted releases.
    *   **Diff Operations:** `diff` (compare two release manifests by hash or tag, return structured diff).
    *   **Transport (Deferred):** The API is in-process for POC (library calls). **Trigger to add network transport:** when the CLI runs on a different machine than the store, or when Microvisor needs to call the API remotely.

### Feature 6: Release Manifest & Runtime Contract
The release manifest is the build system's primary output and Microvisor's primary input. It fully describes a rootfs assembly.

*   **Operator Story (Deploy from Manifest):** "As a deploy operator, I need the release manifest to contain everything Microvisor needs to assemble a rootfs — the ordered layer list, each layer's content address, and any runtime metadata — so that deploy is a single manifest-driven operation."
*   **Operator Story (Manifest Inspection):** "As a platform engineer, I need to read a release manifest and immediately understand what layers compose the rootfs, in what order, and what changed since the last release."
*   **Operator Story (Workload Metadata):** "As a workload provider, I need the manifest to carry runtime metadata (memory requirements, vCPU count, network policy hints) alongside the layer stack, so that Microvisor can configure the VM without a separate config step."
*   **Feature Details:**
    *   **Manifest Contents:** Ordered layer list (each entry: layer name, content address, size, parent address), build metadata (build ID, timestamp, Dockerfile hash), workload/runtime metadata (configurable per `steel_release` stage).
    *   **Manifest Format:** JSON. Machine-readable, diffable, versionable.
    *   **Microvisor Contract:** Microvisor reads the manifest, pulls any layers not already cached locally from the store, and assembles the rootfs using its dm-thin CoW snapshot infrastructure. The build system's responsibility ends at producing a valid manifest and ensuring all referenced layers are in the store.

## 4. Open Design Questions (To Be Resolved in TAD)

### Layer Format and Assembly Strategy
The build system must produce layered artifacts. Microvisor must assemble them into a rootfs. The format layers take determines how both the build and runtime work. Three options are under consideration (file-level tarballs flattened at deploy, file-level tarballs composed via overlayfs, block-level dm-thin snapshots). See the one-pager (`docs/000-one-pager.md`) for the full tradeoff analysis. This decision will be locked in the TAD.

### Docker/BuildKit Integration Depth
The build system uses Docker/BuildKit as its execution engine. The TAD needs to decide the integration depth:
- **Shallow:** Shell out to `docker build --target <stage>`, then `docker export` to extract the filesystem. Simple, but limited control over caching and layer extraction.
- **Medium:** Use BuildKit's Go/gRPC API to drive builds programmatically, with fine-grained control over cache mounts, output formats, and parallel execution.
- **Deep:** Use BuildKit as a library, managing the build graph directly.

### Steel Label Convention
The exact label schema for annotating Dockerfile stages (`steel.layer`, `steel.release`, ordering, metadata) needs to be defined in the TAD. Key decisions: whether ordering is explicit (label-based) or implicit (FROM-chain order), how the `steel_release` stage declares its layer list, and what additional metadata labels the build system supports.

## 5. Out of Scope (With Re-evaluation Triggers)

| Item | Trigger to Revisit |
|---|---|
| Manifest signing | Releases consumed by hosts the build operator doesn't directly control, or compliance mandates signed artifacts. |
| Network API transport | CLI or Microvisor runs on a different machine than the store. |
| Layer-level file diff | Manifest-level diff is insufficient for triage — operators regularly need file-level change detail within a layer. |
| Parallel layer builds | Single-machine build throughput becomes a bottleneck. Sequential is correct first; parallel is an optimization. |
| Custom build engine (non-Docker) | Docker/BuildKit introduces unacceptable overhead, or we need build-level controls Docker can't provide. |

*Note: Store-specific deferrals (distributed replication, automated GC) live in the `fs-storage` PRD.*
