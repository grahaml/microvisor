# Technical Architecture Document (TAD): Microvisor Build System

This document maps the PRD (`docs/001-prd.md`) to a concrete technical design. It specifies the build pipeline, data formats, integration points, and abstraction boundaries for the Microvisor Build System.

---

## 1. System Prerequisites

### 1.1 Build Host
| Requirement | Purpose |
|---|---|
| BuildKit daemon (`buildkitd`) | Stage execution engine. Runs standalone — no Docker daemon required. |
| `e2fsprogs` ≥ 1.43 | `mke2fs -d` for creating ext4 images from directories without mounting. |
| `zstd` | Layer compression/decompression. |
| `fs-storage` | Content-addressed layer store (local or reachable via API). |
| Sufficient scratch disk | BuildKit working space + ext4 staging. Scales with layer size. |

BuildKit is the only required daemon. The build system itself is a CLI/library process that talks to BuildKit via gRPC and to `fs-storage` via its API.

### 1.2 Runtime Host (Microvisor)
| Requirement | Purpose |
|---|---|
| dm-thin pool (`microvisor-pool`) | Target for layer import. Already required by Microvisor Spec-001. |
| `zstd` | Decompressing layers pulled from the store. |
| `fs-storage` access | Pulling layers and release manifests. |

The runtime host does not need BuildKit or any build tooling. It only needs to decompress and import layers.

## 2. Architecture Overview

### 2.1 Components

```
┌─────────────────────────────────────────────────────┐
│                   Build System                       │
│                                                      │
│  ┌──────────┐   ┌──────────┐   ┌────────────────┐  │
│  │Dockerfile│──▶│  Build    │──▶│    Layer        │  │
│  │  Parser  │   │Orchestrator│  │  Converter      │  │
│  └──────────┘   └─────┬─────┘  └───────┬─────────┘  │
│                       │                 │            │
│                       ▼                 ▼            │
│               ┌──────────────┐  ┌──────────────┐    │
│               │   BuildKit   │  │  fs-storage   │    │
│               │   (gRPC)     │  │  (client)     │    │
│               └──────────────┘  └──────────────┘    │
└─────────────────────────────────────────────────────┘
```

**Dockerfile Parser:** Reads the Dockerfile, extracts multi-stage structure and Steel label annotations, produces a build graph.

**Build Orchestrator:** Walks the build graph in dependency order. For each stage: checks `fs-storage` for cache hit (by input hash), delegates to BuildKit on cache miss, hands the result to the Layer Converter.

**Layer Converter:** Takes BuildKit's filesystem output (directory) and produces the store artifact (zstd-compressed ext4 image). Sits behind the `LayerFormat` abstraction boundary.

**BuildKit (gRPC):** Executes Dockerfile stages in isolated containers. Accepts injected cache sources for parent stages.

**fs-storage (client):** Content-addressed store for layers and release manifests. The build system is a producer and consumer.

### 2.2 Data Flow

```
Dockerfile
    │
    ▼
Parse: extract stages, labels, build graph
    │
    ▼
For each stage (dependency order):
    │
    ├─ Compute input hash (SHA-256 of stage definition + parent hash)
    │
    ├─ Check fs-storage ──▶ HIT: skip build, inject into BuildKit cache for downstream stages
    │
    └─ MISS:
        ├─ Inject cached parent layers into BuildKit as named contexts
        ├─ BuildKit Solve() targeting this stage
        ├─ Export stage filesystem as directory
        ├─ mke2fs -d → ext4 image
        ├─ Compute output hash (SHA-256 of ext4 image)
        ├─ zstd compress
        └─ Publish to fs-storage (artifact + metadata)
    │
    ▼
Generate release manifest JSON from steel_release labels + layer metadata
    │
    ▼
Publish release manifest to fs-storage
```

## 3. Subsystem Specifications

### 3.1 Dockerfile Parser & Steel Label Convention

#### Label Schema

| Label | Required | Scope | Description |
|---|---|---|---|
| `steel.layer` | Yes (on layer stages) | Stage | Layer name identifier. Must be unique within the Dockerfile. Example: `steel.layer="base-os"` |
| `steel.layer.order` | Yes (on layer stages) | Stage | Integer position in the layer stack. `0` is the bottom. Example: `steel.layer.order="0"` |
| `steel.release` | Yes (exactly one stage) | Stage | Marks the release entry point. Value: `"true"`. |
| `steel.release.layers` | Yes (on release stage) | Stage | Comma-separated ordered list of layer names. Example: `steel.release.layers="base-os,platform,chrome,app"` |
| `steel.meta.*` | Optional | Stage | Arbitrary key-value metadata passed through to the release manifest. Example: `steel.meta.vcpus="2"`, `steel.meta.memory_mb="512"` |

#### Example Dockerfile

```dockerfile
FROM debian:bookworm-slim AS base_os
LABEL steel.layer="base-os"
LABEL steel.layer.order="0"
RUN apt-get update && apt-get install -y --no-install-recommends \
    ca-certificates curl systemd-sysv \
    && rm -rf /var/lib/apt/lists/*

FROM base_os AS platform
LABEL steel.layer="platform"
LABEL steel.layer.order="1"
COPY steel-init /usr/local/bin/steel-init
COPY steel-agent /usr/local/bin/steel-agent
RUN chmod +x /usr/local/bin/steel-*

FROM platform AS chrome
LABEL steel.layer="chrome"
LABEL steel.layer.order="2"
RUN apt-get update && apt-get install -y --no-install-recommends \
    chromium chromium-sandbox fonts-liberation \
    && rm -rf /var/lib/apt/lists/*

FROM chrome AS app
LABEL steel.layer="app"
LABEL steel.layer.order="3"
COPY steel-browser-server /usr/local/bin/
COPY config/ /etc/steel/

FROM scratch AS steel_release
LABEL steel.release="true"
LABEL steel.release.layers="base-os,platform,chrome,app"
LABEL steel.meta.vcpus="4"
LABEL steel.meta.memory_mb="4096"
LABEL steel.meta.workload_type="steel-browser"
```

The `steel_release` stage is `FROM scratch` — it has no filesystem. It exists solely to carry the release metadata as labels. The build system reads these labels and generates the release manifest JSON; it does not build this stage via BuildKit.

#### Parser Output

The parser produces a **build graph**: an ordered list of stage descriptors, each containing:
- Stage name (from `AS <name>`)
- Parent stage name (from `FROM <parent> AS <name>`)
- Steel labels (parsed from `LABEL` instructions)
- Raw Dockerfile instructions for the stage (used for input hash computation)
- Position in the Dockerfile (byte offsets, for error reporting)

The parser validates:
- Exactly one stage has `steel.release="true"`.
- All layer names referenced in `steel.release.layers` correspond to stages with `steel.layer` labels.
- `steel.layer.order` values are contiguous integers starting at 0.
- No duplicate layer names.

### 3.2 BuildKit Integration (gRPC API)

The build system communicates with BuildKit via its gRPC API. This is the "medium" integration depth from the PRD — programmatic control over builds without managing BuildKit's internal graph representation.

#### BuildKit Daemon Lifecycle
BuildKit (`buildkitd`) runs as a standalone daemon on the build host. The build system connects to it via a Unix socket or TCP endpoint. The build system does not manage `buildkitd`'s lifecycle — it is a system service.

#### Per-Stage Build via Solve()

For each stage that is a cache miss, the build system calls BuildKit's `Solve()` RPC:

```
Solve request:
  Frontend:    "dockerfile.v0"
  Source:      local Dockerfile + build context
  Options:
    target:    "<stage_name>"            # build only up to this stage
    context:<parent_stage>=oci-layout://<path>  # inject cached parent
  Exporter:    "local"                   # export as directory
  ExportDir:   "/tmp/steel-build/<stage_name>/"
```

**Cache injection for parent stages:** When a parent stage is a cache hit (exists in `fs-storage`), the build system must provide its filesystem to BuildKit so downstream stages can build on top of it. The mechanism:

1. Pull the parent layer's **OCI artifact** from `fs-storage` (zstd-compressed OCI tar — see Section 3.4 for the dual-format store strategy).
2. Decompress: `zstd -d layer.oci.tar.zst -o layer.oci.tar`.
3. Unpack to OCI image layout directory.
4. Provide to BuildKit as a named context override: `--opt context:<parent_stage>=oci-layout://<path>`.

BuildKit resolves `FROM <parent_stage>` to the injected OCI image instead of building the parent stage. This is the key mechanism that avoids redundant rebuilds.

Because the store holds OCI artifacts natively (see Section 3.4), cache injection requires only a decompress + untar — no format conversion. This eliminates the ext4→OCI conversion bottleneck that would otherwise add 4-6 seconds per cached parent layer per build.

**Optimization:** During a single build session where multiple stages are built sequentially, BuildKit's internal cache remains warm. If Stage 1 is built via BuildKit (cache miss), BuildKit already has Stage 1's output for building Stage 2. The OCI pull path is only needed when a parent stage was loaded from `fs-storage` (cache hit) and a child stage needs building (cache miss).

#### Stage Output Extraction

BuildKit's `local` exporter writes the stage's filesystem to a directory. This directory is the input to the Layer Converter (Section 3.4). The directory contains the full filesystem state at the end of that stage — not a delta from the parent. The delta is computed implicitly by the content address chain (see Section 3.3).

### 3.3 Content Addressing (Hybrid)

Each layer carries two hashes:

| Hash | When Computed | Purpose |
|---|---|---|
| **Input hash** | Before build | Fast cache lookup. Determined from the stage definition without executing anything. |
| **Output hash** | After build | Content verification. The true fingerprint of what was produced. |

#### Input Hash Computation

```
input_hash = SHA-256(
    parent_input_hash          # empty string for base layers (order=0)
    + "\0"
    + canonical_stage_definition  # Dockerfile instructions for this stage, normalized
)
```

**Normalization of stage definition:** The Dockerfile instructions for the stage are extracted and canonicalized before hashing:
- Whitespace normalized (collapse runs, trim trailing).
- Comments stripped.
- `ARG` values resolved (build args are part of the input).
- `COPY --from=` references resolved to the referenced stage's input hash.
- The base image reference (`FROM <image>`) is resolved to its digest (e.g., `debian:bookworm-slim` → `sha256:abc...`). This ensures that an upstream base image update changes the input hash.

The input hash is the **cache lookup key**. If `fs-storage` contains a layer with this input hash, the build is skipped.

#### Output Hash Computation

```
output_hash = SHA-256(contents of the ext4 image file, before zstd compression)
```

The output hash is computed over the raw ext4 image bytes. It is recorded in the layer metadata and verified on every pull from `fs-storage`. If a pull returns content whose SHA-256 doesn't match the stored output hash, the layer is rejected as corrupt or tampered.

#### Non-Determinism Policy (POC)

For POC, the build system trusts the cache: if the input hash matches, the cached layer is used without re-verification. The output hash is recorded for integrity checking (corruption/tampering), not for non-determinism detection.

**Trigger to add non-determinism detection:** When an operator reports a regression caused by a cached layer containing stale content (e.g., a security patch was applied to an upstream package but the layer wasn't rebuilt because the Dockerfile didn't change). At that point, implement periodic "audit builds" that rebuild cached layers and compare output hashes.

### 3.4 Layer Format & Conversion Pipeline

#### Dual-Format Store Strategy

Each layer is stored in `fs-storage` as **two artifacts** produced from the same source directory:

| Artifact | Format | Consumer | Purpose |
|---|---|---|---|
| **Deploy artifact** | zstd-compressed ext4 image (`.ext4.zst`) | Microvisor | Streamed directly into dm-thin volume at deploy time. |
| **Build-cache artifact** | zstd-compressed OCI tar (`.oci.tar.zst`) | BuildKit | Injected as a named context override for cache-hit parent stages. |

Both artifacts are produced at build time from the same BuildKit export directory. Neither the build path nor the deploy path ever needs to convert between formats — each consumer pulls the artifact in the format it needs.

**Storage overhead:** ~2x compressed size per layer (both formats compressed with zstd). A 1GB uncompressed layer becomes ~300MB ext4.zst + ~300MB oci.tar.zst = ~600MB total. This is per unique layer (content-addressed deduplication across releases), and storage cost is negligible compared to the per-build conversion overhead it eliminates.

#### Pipeline: BuildKit Output → Dual Store Artifacts

```
BuildKit export directory (/tmp/steel-build/<stage>/)
    │
    ├──────────────────────────────────┐
    │ (parallel)                       │ (parallel)
    ▼                                  ▼
DEPLOY ARTIFACT                    BUILD-CACHE ARTIFACT
    │                                  │
mke2fs -t ext4 -d <dir> <stage>.ext4  tar -cf <stage>.oci.tar <dir>
    │                                  │  + OCI manifest + config JSON
    ▼                                  ▼
SHA-256(<stage>.ext4)              zstd -19 <stage>.oci.tar
    │  Output hash                     │
    ▼                                  ▼
zstd -19 <stage>.ext4              <stage>.oci.tar.zst
    │                                  │
    ▼                                  ▼
<stage>.ext4.zst                   Ready for publish
    │                                  │
    └──────────────┬───────────────────┘
                   │
                   ▼
         Publish both artifacts + metadata to fs-storage
```

The two conversion paths run in parallel — there is no dependency between them. Total conversion time is dominated by the slower of the two (typically the ext4 path for large layers).

**`mke2fs -d` rationale:** This is the same technique Microvisor's Spec-008 uses for metadata drives. It creates a fully populated ext4 filesystem from a host directory without ever mounting it — no `CAP_SYS_ADMIN`, no loop devices, fully declarative. The flag requires e2fsprogs ≥ 1.43, which is standard on any modern Linux.

**OCI tar creation:** The OCI layout is a tar archive containing the layer's filesystem as a single OCI layer, plus a minimal `oci-layout`, `index.json`, and image manifest. This is the format BuildKit's `--opt context:<name>=oci-layout://` expects. Creation is a single `tar` pass over the export directory plus three small JSON files.

**zstd compression level:** `-19` is a high compression level. Build-time cost (seconds per layer) is acceptable because builds are not on the latency-critical path. Decompression speed is constant regardless of compression level — zstd decompresses at multi-GB/s. If build-time compression becomes a bottleneck, drop to `-3` or `-6`. **Trigger:** compression time exceeds 10% of total layer build time for large layers.

**Image sizing:** The ext4 image must be large enough to hold the directory contents. Computed as: `du -sb <directory>` + 10% headroom + ext4 metadata overhead, rounded up to the nearest 4MB boundary. Minimum 64MB to avoid ext4 fragmentation edge cases.

#### Format Abstraction Boundary

The conversion pipeline sits behind a `LayerFormat` interface:

```
trait LayerFormat {
    /// Convert a filesystem directory to store artifacts.
    /// Returns both the deploy artifact and the build-cache artifact.
    fn pack(source_dir: &Path, output_dir: &Path) -> Result<LayerArtifacts>;

    /// Extract the build-cache artifact to an OCI layout directory (for BuildKit injection).
    fn unpack_for_build(&self, artifact_path: &Path, target_dir: &Path) -> Result<()>;

    /// Extract the deploy artifact to a raw image (for Microvisor import).
    fn unpack_for_deploy(&self, artifact_path: &Path, target_path: &Path) -> Result<()>;

    /// Compute the output hash of the deploy artifact.
    fn content_hash(artifact_path: &Path) -> Result<ContentHash>;
}

struct LayerArtifacts {
    deploy_artifact: PathBuf,       // e.g., <stage>.ext4.zst
    build_cache_artifact: PathBuf,  // e.g., <stage>.oci.tar.zst
    output_hash: ContentHash,       // SHA-256 of raw ext4 bytes
}
```

The POC implementation is `ZstdExt4OciFormat`. A future format pivot (e.g., squashfs for deploy artifacts) would implement the same trait. The `BuildOrchestrator` and `StoreClient` never handle layer artifacts directly — they go through `LayerFormat`.

### 3.5 Store Integration (`fs-storage` Client)

The build system talks to `fs-storage` through a `StoreClient` interface:

```
enum ArtifactFormat {
    Deploy,     // ext4.zst — for Microvisor import
    BuildCache, // oci.tar.zst — for BuildKit cache injection
}

trait StoreClient {
    /// Resolve an input hash to a content hash. Returns None if not in store.
    /// This is the cache-hit lookup path (< 5ms target).
    fn resolve_input_hash(input_hash: &InputHash) -> Result<Option<ContentHash>>;

    /// Check whether a layer exists by content hash.
    fn has_layer(content_hash: &ContentHash) -> Result<bool>;

    /// Pull a specific artifact format for a layer by content hash.
    fn pull_layer(
        content_hash: &ContentHash,
        format: ArtifactFormat,
        target_path: &Path,
    ) -> Result<LayerMetadata>;

    /// Publish both artifacts for a layer. Idempotent — no-op if content hash already exists.
    fn publish_layer(artifacts: &LayerArtifacts, metadata: &LayerMetadata) -> Result<()>;

    /// Publish a release manifest. Returns the manifest ID.
    fn publish_manifest(manifest: &ReleaseManifest) -> Result<ManifestId>;

    /// Pull a release manifest by ID or tag name.
    fn pull_manifest(id: &ManifestId) -> Result<ReleaseManifest>;

    /// Tag operations
    fn create_tag(name: &str, manifest_id: &ManifestId) -> Result<()>;
    fn resolve_tag(name: &str) -> Result<ManifestId>;
    fn list_tags() -> Result<Vec<(String, ManifestId)>>;
    fn delete_tag(name: &str) -> Result<()>;
}
```

**Two-level addressing.** The store uses two hash spaces: **input hashes** (computed by the build system from stage definitions, used as cache lookup keys) and **content hashes** (SHA-256 of artifact bytes, used as blob storage keys). The `resolve_input_hash` call maps between the two. The build system's cache-hit flow is: `resolve_input_hash(input_hash) → Some(content_hash) → pull_layer(content_hash, format)`.

**Format-aware pull.** The caller specifies which artifact format it needs. The build orchestrator pulls `BuildCache` (OCI tar) for cache injection into BuildKit. Microvisor pulls `Deploy` (ext4) for thin volume import. The store holds both artifacts under the same content hash.

**Idempotent publish.** Publishing a layer with a content hash that already exists in the store is a no-op. The store verifies incoming bytes match the claimed content hash at write time.

**Tags.** Mutable named pointers to release manifests. Used for promotion workflows (`production`, `staging`, `canary`). The diff API accepts tags as well as manifest IDs, so `diff production staging` works directly.

**Key design points:**
- Each layer carries both `input_hash` and `output_hash`.

- `manifest_id` is generated by the build system (timestamp + short random suffix). It is a human-readable identifier, not a content hash.
- `schema_version` enables forward-compatible manifest evolution.

### 3.7 Deploy Path (Microvisor Integration)

This section describes how Microvisor consumes the build system's output. This is the contract between the two systems.

#### Layer Import Sequence

When Microvisor receives a release manifest (via `fs-storage` or direct handoff), it imports layers into its dm-thin pool:

```
For each layer in manifest.layers (order 0 → N):
    │
    ├─ Check local thin pool: does a thin volume for this input_hash exist?
    │   YES → skip (layer already imported)
    │
    └─ NO:
        ├─ Pull <input_hash>.ext4.zst from fs-storage
        ├─ Verify: SHA-256(decompress(artifact)) == output_hash
        ├─ Create a new thin volume in the pool (DM_TARGET_MSG create_thin)
        ├─ Activate the thin volume (DM_DEV_CREATE → DM_TABLE_LOAD → DM_DEV_SUSPEND/resume)
        ├─ Stream decompress + write: zstd -d < layer.ext4.zst | dd of=/dev/mapper/<vol> bs=4M
        └─ Deactivate thin volume (keep in pool for snapshotting)
```

**Layer caching on the runtime host:** Once a layer's thin volume exists in the pool, it persists across VM boots. Importing is a one-time cost per layer per host. Subsequent VM launches snapshot the existing thin volume — the same `DM_TARGET_MSG create_snap` flow from Microvisor Spec-008.

#### RootFS Assembly

Microvisor does **not** compose layers at runtime using overlayfs or multi-device stacking. Instead, it assembles a flat rootfs:

The final layer (highest order) in the stack IS the complete rootfs — because each Docker stage builds on top of its parent via `FROM`. Layer 3 (`app`) contains everything from layers 0-2 plus its own additions. The build system exports each stage's **full filesystem**, not a delta.

This means:
- Microvisor only needs to import the **final layer** to get a complete rootfs.
- Lower layers are stored in `fs-storage` for caching and diffing purposes, but at deploy time only the top layer is imported into the thin pool.
- The thin volume for the top layer becomes the base image. Per-VM CoW snapshots are created on top of it, exactly as Microvisor does today.

**Why store all layers if only the top one is deployed?**
- **Cache reuse:** If only the app layer changes, the build system skips rebuilding layers 0-2. The intermediate layers are the cache entries.
- **Diffing:** Comparing two releases at the layer level shows exactly which component changed.
- **Shared base layers:** Multiple workload types can share `base-os` and `platform` layers. The build system deduplicates at the layer level, even though the final deployed image is a single flat artifact.

#### Deploy Flow Summary

```
Release manifest arrives (by manifest hash or tag resolution)
    │
    ▼
Pull top layer (highest order) deploy artifact from fs-storage by content hash
    │
    ▼
Decompress zstd stream, compute SHA-256 of raw ext4 bytes
    │
    ├─ SHA-256 matches manifest's output_hash → proceed
    └─ Mismatch → reject layer, abort deploy (corrupt or tampered artifact)
    │
    ▼
dd verified ext4 into new thin volume
    │
    ▼
Thin volume is the base image for this release
    │
    ▼
Per-VM launch: DM_TARGET_MSG create_snap → CoW snapshot → Firecracker O_DIRECT
```

## 4. Build Pipeline: End-to-End Sequence

A complete build, from Dockerfile to published release:

```
1. PARSE
   Input:  Dockerfile
   Output: Build graph (stages, labels, dependencies)
   Action: Parse Dockerfile, extract Steel annotations, validate schema.

2. PLAN
   Input:  Build graph
   Output: Ordered build plan (which stages to build, which to skip)
   Action: For each stage in dependency order, compute input hash.
           Query fs-storage for each input hash.
           Mark each stage as HIT (skip) or MISS (build).

3. BUILD (for each MISS, in dependency order)
   Input:  Stage definition + parent layer (from fs-storage or previous build step)
   Output: Filesystem directory
   Action: If parent was a HIT: pull OCI artifact from fs-storage (BuildCache format),
             decompress, unpack to OCI layout directory,
             inject into BuildKit as named context override.
           If parent was a MISS: BuildKit already has it from the previous build step.
           Call BuildKit Solve() targeting this stage.
           Export stage filesystem to directory.

4. CONVERT (for each newly built stage, in parallel)
   Input:  Filesystem directory
   Output: Dual artifacts — ext4.zst (deploy) + oci.tar.zst (build-cache) + output hash
   Action: In parallel:
             a) mke2fs -d → ext4 image → SHA-256 (output hash) → zstd -19 compress.
             b) tar + OCI manifest → OCI tar → zstd -19 compress.

5. PUBLISH (for each newly built stage)
   Input:  Both compressed artifacts + metadata (input hash, output hash, provenance)
   Output: Layer stored in fs-storage (both formats)
   Action: Call fs-storage publish API with both artifacts.

6. MANIFEST
   Input:  Build graph + layer metadata (all stages, HIT and MISS)
   Output: Release manifest JSON
   Action: Assemble manifest from steel_release labels + per-layer metadata.
           Publish manifest to fs-storage.
```

## 5. Abstraction Boundaries

Three interfaces isolate the build system from implementation details that may change:

### 5.1 `LayerFormat`
Encapsulates how filesystem directories become dual-format store artifacts and vice versa.
- **POC implementation:** `ZstdExt4OciFormat` (mke2fs -d + OCI tar + zstd for both).
- **Future candidate (deploy artifact):** `SquashfsOciFormat` (squashfs replaces ext4 for the deploy artifact; OCI build-cache artifact unchanged). Drop-in replacement via the same trait.
- **Trigger to pivot deploy format:** need for at-rest inspectability (mount and browse layers without decompressing), or better compression ratios for specific content profiles.
- **The build-cache artifact (OCI tar) is stable.** It is dictated by BuildKit's input requirements and is unlikely to change unless the build engine changes.

### 5.2 `StoreClient`
Encapsulates how the build system talks to `fs-storage`.
- **POC implementation:** Direct filesystem operations (local store).
- **Future candidate:** HTTP/gRPC client for a remote store.
- **Trigger to pivot:** builds run on a different machine than the store, or Microvisor nodes need remote layer pulls.

### 5.3 `BuildEngine`
Encapsulates how Dockerfile stages are executed.
- **POC implementation:** BuildKit gRPC client.
- **Future candidate:** Direct container execution (e.g., `youki`/`crun` + custom overlay), or Firecracker-based builds (dogfooding Microvisor).
- **Trigger to pivot:** BuildKit introduces unacceptable overhead, or we need build-level controls BuildKit can't provide (e.g., cgroup fencing of build processes to isolated cores).

## 6. Security Architecture

### 6.1 Build-Time Security
| Concern | Mitigation |
|---|---|
| **Malicious Dockerfile instructions** | BuildKit executes each `RUN` in an isolated container with a restricted seccomp profile. The build system does not execute Dockerfile instructions directly. |
| **Supply chain (base images)** | Input hash computation resolves `FROM <image>` to its registry digest, not the mutable tag. A base image update changes the input hash and triggers a rebuild. |
| **Build host compromise** | Build provenance metadata records the build host identifier. If a host is compromised, all layers built on it can be identified and quarantined. |
| **Compromised BuildKit** | Output hash verification on every pull from the store catches tampered layer content regardless of how it was produced. |

### 6.2 Store Security
| Concern | Mitigation |
|---|---|
| **Layer tampering in store** | Store verifies content hash at publish time (write-time integrity). Consumers verify output hash on pull (consumer-side integrity). `verify_store` scan detects at-rest corruption. |
| **Silent overwrite** | Append-only semantics at the blob level. Publishing different content under an existing content hash is rejected by the store (`StoreError::HashCollision`). |
| **Unauthorized publish** | Deferred (see Section 7). POC assumes a trusted build environment. |

### 6.3 Deploy-Time Security
| Concern | Mitigation |
|---|---|
| **Corrupt layer during transfer** | Microvisor decompresses the ext4.zst stream, computes SHA-256 of the raw ext4 bytes, compares against the `output_hash` from the release manifest. Mismatch → reject the layer, do not write to thin volume. Verification is the consumer's responsibility, not the store's — the store streams bytes without inline verification. |
| **Stale layers** | Input hash chain ensures that a change to any lower layer invalidates all layers above it. A manifest cannot reference a stale intermediate layer alongside a fresh top layer. |

## 7. Deferred Items (With Re-evaluation Triggers)

| Item | POC Approach | Production Approach | Trigger |
|---|---|---|---|
| Non-determinism detection | Trust cache; record output hash for integrity only | Periodic audit builds comparing output hashes | Operator reports regression from stale cached layer |
| Parallel stage builds | Sequential (dependency order) | BuildKit concurrent solves for independent stages | Build throughput becomes a bottleneck |
| Deploy format pivot (squashfs) | zstd ext4 behind `LayerFormat` trait | Swap deploy artifact to squashfs; build-cache artifact (OCI) unchanged | Need at-rest inspectability or better compression |
| Remote store | Local filesystem `fs-storage` | HTTP/gRPC `StoreClient` implementation | Multi-machine builds or remote Microvisor pulls |
| Manifest signing | No signing; trusted build environment | Ed25519 or similar signatures on release manifests | Releases consumed by hosts outside builder's control |
| Build authorization | No auth; any caller can publish | API keys or mTLS for publish operations | Multi-user or CI/CD environments |
| Single-format store | Dual artifacts (ext4.zst + oci.tar.zst) | If storage cost becomes prohibitive, derive one format from the other on demand | Storage per layer exceeds budget; currently ~2x compressed size |
| Dockerfile parse caching | Re-parse on every build | Cache parse results keyed by Dockerfile hash | Parse time becomes measurable fraction of build time |
