# Product Requirements Document (PRD): fs-storage (Layer Store)

## 1. Product Objective
To provide a persistent, content-addressed backing store for layer artifacts and release manifests produced by the Microvisor build system. The store must be backend-agnostic from day one: the build system calls a typed Rust API; that API is satisfied by a pluggable implementation. The local filesystem implementation ships first. Any future backend (S3, GCS, shared NAS) is a drop-in at the implementation boundary, with no changes to the build system or the store's public API.

**Performance targets:**
| Operation | Target |
|---|---|
| Cache-hit lookup (`resolve_input_hash` + `has_layer`) | < 5 ms |
| Manifest query (`list_builds`, `get_manifest`) | < 100 ms |
| Blob write (`publish_layer`) | < 1 s non-I/O overhead; total bounded by disk throughput |
| Blob read (`pull_layer`) | first-byte latency < 10 ms; throughput bounded by disk I/O |
| GC identification (`gc_candidates`) | < 5 s for stores up to 10,000 layers |
| Tag operation (`create_tag`, `get_tag`) | < 10 ms |

**Core invariants:**
- **Blobs are immutable once written.** A content hash permanently identifies exactly one set of bytes. There is no update operation for blobs.
- **Publish is idempotent.** Publishing a layer or manifest that already exists in the store is a no-op, not an error.
- **Integrity is verified at publish time and via explicit scan.** `publish_layer` verifies the content hash of incoming bytes before writing. A manual `verify_store` scan re-hashes all blobs on demand. Per-pull inline verification is the consumer's responsibility (Microvisor validates output hash after decompression; the store streams bytes without inline verification).
- **The backend trait is the only coupling point.** No caller above `StorageBackend` may use filesystem paths, S3 URLs, or any backend-specific primitive directly.

---

## 2. Target Audience

**Build Operators:** Run builds, publish artifacts to the store, query build history, tag releases for promotion. Need fast cache-hit lookups and confidence that published artifacts are immutable.

**Deploy Operators:** Pull layers from the store by content address and stream them directly to dm-thin for rootfs assembly. Need streaming pull with low first-byte latency — layers are zstd-compressed ext4 blobs that are piped directly into dm-thin and must not be fully materialised in memory.

**Platform Engineers:** Query build history, diff releases, run garbage collection. Need a queryable catalog.

**Security Engineers:** Verify store integrity via explicit scan. Confirm the immutability contract holds. Detect tampering before it reaches a deploy.

**Future Backend Implementors:** Implement `StorageBackend` for a new storage system (S3, GCS, etc.) and drop it in without touching any other module. Need a minimal, well-specified trait contract.

## 3. Core Features & Operator Stories

### Feature 1: StorageBackend Trait — The Abstraction Boundary

The `StorageBackend` trait is the only interface between the store's logic and the storage medium. Implementations provide raw blob and metadata primitives; all layer-aware semantics live in `LayerStore` above the trait.

- **Operator Story (Backend Swap):** "As a future backend implementor, I need a minimal, well-specified trait to implement so that I can add S3 support without understanding layer hashing, GC reference counting, or manifest structure."
- **Operator Story (No Leakage):** "As a build system maintainer, I need the build system to call `LayerStore` methods with no knowledge of the underlying storage medium, so that a storage migration never requires changes outside the `fs-storage` crate."
- **Operator Story (Testability):** "As a developer writing tests for the build system, I need to provide a fast in-memory implementation of `StorageBackend` so that tests don't touch the filesystem."

**Feature Details:**
- The trait exposes two namespaces: blob operations (content-addressed, binary, format-aware) and metadata operations (key/value, structured text).
- Blob operations: `has_blob(hash, format)`, `put_blob(hash, format, reader: impl AsyncRead)`, `get_blob(hash, format) -> impl AsyncRead`, `delete_blob(hash, format)`. The `format: ArtifactFormat` parameter distinguishes between `Deploy` (ext4.zst) and `BuildCache` (oci.tar.zst) artifacts stored under the same content hash.
- Metadata operations: `put_meta(key, value)`, `get_meta(key)`, `list_meta(prefix)`, `delete_meta(key)`.
- All methods return `Result<T, StoreError>`. The error type is defined in `fs-storage` and backend implementations map their internal errors to it.
- The trait makes no guarantees about atomicity or durability beyond what the implementation documents. `LocalJsonBackend` documents POSIX atomicity (`rename`). An `S3Backend` would document eventual consistency.
- Blob operations are streaming: `put_blob` consumes an `AsyncRead`; `get_blob` returns one. This means the trait cannot be trivially object-safe with `impl Trait` in method signatures — the concrete approach (generic parameter vs. boxed trait object) is an implementation decision.

### Feature 2: LocalJsonBackend — Filesystem Implementation

The local filesystem implementation of `StorageBackend`. First implementation at POC. Metadata is stored as flat JSON files. Optimised for single-machine builds with no external service dependencies.

- **Operator Story (Zero Infrastructure):** "As a build operator on a single machine, I need the store to work with no external services — no database, no object store, no daemon — so that I can start building immediately after cloning the repo."
- **Operator Story (Human Inspection):** "As a platform engineer debugging a build, I need to inspect the on-disk layout of the store with standard tools (`ls`, `cat`, `sha256sum`) so that I don't need special tooling to investigate a suspected corruption."
- **Operator Story (Safe Concurrent Writes):** "As a build operator running two builds in parallel, I need the store to handle concurrent `put_blob` calls without corruption, so that parallel builds don't require external locking."

**Feature Details:**

**On-disk layout:**
```
{store-root}/
  objects/
    {sha256[0:2]}/
      {sha256[2:]}.ext4.zst      ← deploy artifact (zstd-compressed ext4 image)
      {sha256[2:]}.oci.tar.zst   ← build-cache artifact (zstd-compressed OCI tar)
  manifests/
    {manifest-hash}.json    ← full release manifest, stored by its own content hash
  meta/
    layers/
      {content-hash}.json   ← per-layer provenance (see Feature 3a)
    index/
      {input-hash}          ← plain text file: content hash (input hash → content hash lookup)
    builds/
      {build-id}.json       ← build catalog entry
  refs/
    tags/
      {tag-name}            ← plain text file: one manifest hash, no trailing newline
  tmp/
    {uuid}                  ← staging area for in-progress writes
```

Each layer has two blob artifacts stored under the same content hash with different format suffixes. The `meta/index/` directory maps input hashes (build system cache keys) to content hashes (blob storage keys). This two-level addressing allows the build system to look up layers by input hash (fast, no build required) while the store indexes blobs by content hash (immutability guarantee).

**Atomicity:** All blob and metadata writes go to `tmp/{uuid}` first, then `rename` into their final path. On POSIX filesystems, `rename` within the same filesystem is atomic. The `tmp/` directory is cleaned on store open (any file in `tmp/` at startup is an incomplete write from a crashed process).

**Deduplication:** `put_blob` checks for the blob's final path (including format suffix) before writing. If it exists, the write is skipped entirely. No copy, no hash recomputation.

**Directory creation:** `objects/{prefix}/` directories are created on first use with `create_dir_all`. Concurrent writers racing to create the same prefix directory is handled by treating `ErrorKind::AlreadyExists` as success.

**No file locking:** The combination of content-addressing and atomic rename makes blob writes safe without file locks. Two concurrent writers for the same hash both write to distinct `tmp/` files and race to rename; one wins, one finds the target already exists and discards its tmp file. The result is identical either way.

**Streaming blobs:** `put_blob` reads from the provided `AsyncRead` into `tmp/{uuid}`, then renames. `get_blob` opens the file and returns a streaming reader — no full read into memory.

### Feature 3: LayerStore — Blob Operations & Input Hash Index

`LayerStore` is the typed API surface that build system and deploy system callers use. It composes a `StorageBackend` and adds layer-level semantics: hash enforcement, collision detection, dual-format storage, input hash indexing, and provenance.

- **Operator Story (Cache Hit):** "As a build system, I need to check whether a layer with a given input hash already exists in the store in under 5 ms, so that the hash-before-build optimisation doesn't add meaningful latency to every stage evaluation."
- **Operator Story (Publish):** "As a build operator, I need to publish both artifacts (deploy + build-cache) for a completed layer to the store and receive confirmation that they are durably stored and content-verified, so that I can proceed to the next layer stage with confidence."
- **Operator Story (Format-Aware Pull):** "As Microvisor assembling a rootfs, I need to pull the deploy artifact (ext4.zst) as a byte stream and pipe it directly to dm-thin. As the build system injecting a cached parent into BuildKit, I need to pull the build-cache artifact (oci.tar.zst). Each consumer pulls the format it needs."
- **Operator Story (Collision Detection):** "As a security engineer, I need the store to reject any attempt to publish bytes under a content hash that already exists in the store with different content, so that hash collision or tampering is surfaced immediately rather than silently overwriting a valid artifact."

**Feature Details:**

**Input hash resolution:**
- `resolve_input_hash(input_hash: &InputHash) -> Result<Option<ContentHash>>`: Reads `meta/index/{input_hash}`. Returns the content hash if the input hash has been published, `None` otherwise. This is the cache-hit lookup path — the build system calls this before deciding whether to build a stage.
- `register_input_hash(input_hash: &InputHash, content_hash: &ContentHash) -> Result<()>`: Writes the mapping to `meta/index/{input_hash}`. Called during `publish_layer`. Idempotent — if the mapping already exists with the same content hash, it's a no-op. If it exists with a *different* content hash, the publish proceeds (the same stage definition can produce different content due to non-determinism; the latest wins). The build system records both hashes in the release manifest for auditability.

**Dual-format publish and pull:**
- `publish_layer(deploy_reader: impl AsyncRead, cache_reader: impl AsyncRead, meta: LayerMeta) -> Result<ContentHash>`: Streams both artifacts into the store, computing the content hash inline from the deploy artifact's uncompressed bytes (the deploy artifact is the source of truth for the content hash). Writes both blobs, the input hash index entry, and the layer provenance metadata. Returns the content hash. Idempotent.
- `has_layer(content_hash: &ContentHash) -> Result<bool>`: Checks for the deploy artifact blob. Both artifacts are published atomically, so checking one is sufficient.
- `pull_layer(content_hash: &ContentHash, format: ArtifactFormat) -> Result<impl AsyncRead>`: Returns a streaming reader over the requested format's blob. The store opens the file and begins streaming immediately — no full read into memory. The caller is responsible for consuming the stream and verifying integrity (Microvisor verifies the output hash after decompression).

**Collision detection:** If a deploy blob for content hash `H` already exists and the bytes being published produce a different hash, `publish_layer` returns `StoreError::HashCollision`. This is a fatal store integrity error.

**`LayerMeta`** carries provenance and operational fields:
```rust
struct LayerMeta {
    input_hash: InputHash,
    content_hash: ContentHash,  // output hash — SHA-256 of raw ext4 bytes
    parent_input_hash: Option<InputHash>,
    uncompressed_size: u64,
    compressed_size_deploy: u64,
    compressed_size_cache: u64,
    // Provenance
    builder_version: String,
    build_timestamp: u64,      // Unix epoch seconds
    build_host: String,
    stage_definition_hash: ContentHash,
    dockerfile_hash: ContentHash,
}
```

- The store treats blob bytes as opaque. It does not decompress, validate filesystem structure, or inspect content. Format interpretation is the caller's responsibility.

### Feature 4: LayerStore — Manifest & Build Catalog

Release manifests and build catalog entries are the store's structured, queryable data. Every completed build publishes exactly one manifest and one catalog entry.

- **Operator Story (Publish Manifest):** "As a build operator completing a release, I need to publish a release manifest to the store and receive a manifest hash, so that Microvisor can retrieve the full assembly spec by that hash."
- **Operator Story (List Builds):** "As a platform engineer, I need to list all builds in the store ordered by date descending, so that I can find recent releases and understand build history."
- **Operator Story (Query by Tag):** "As a deploy operator, I need to retrieve the release manifest for a named tag (e.g., `production`, `staging-latest`) so that I can assemble a rootfs from the current promoted build without knowing its manifest hash."
- **Operator Story (Query by Layer):** "As a platform engineer investigating a layer change, I need to list all builds that reference a given content hash, so that I can understand the blast radius of a layer."
- **Operator Story (Retrieve Manifest):** "As a deploy operator, I need to retrieve a release manifest by hash or by tag, so that I can read the full ordered layer stack and initiate assembly."

**Feature Details:**
- `publish_manifest(manifest: ReleaseManifest) -> Result<ContentHash>`: Serialises manifest to canonical JSON, computes its hash, stores under `manifests/{hash}.json`, writes a build catalog entry. Idempotent.
- `get_manifest(hash: &ContentHash) -> Result<ReleaseManifest>`: Reads and deserialises a manifest by hash. Returns `StoreError::NotFound` if absent.
- `list_builds(filter: BuildFilter) -> Result<Vec<BuildCatalogEntry>>`: Returns catalog entries matching `filter`. `BuildFilter` supports: tag name, date range, layer hash membership, free-text name prefix.
- `get_build(build_id: &BuildId) -> Result<BuildCatalogEntry>`: Direct catalog lookup by build ID.
- **`BuildCatalogEntry`**: `build_id: BuildId`, `release_name: String`, `manifest_hash: ContentHash`, `build_timestamp: u64` (Unix epoch seconds), `spec_hash: ContentHash`, `layers: Vec<ContentHash>` (ordered).
- **Catalog storage:** Each build catalog entry is a JSON file in `meta/builds/{build-id}.json`. `list_builds` scans the directory and deserialises all entries, then filters in-process. **Trigger to migrate to `LocalSQLiteBackend`:** when `list_builds` scan time exceeds 100 ms (approximately 1,000+ builds on typical hardware).
- **Canonical JSON:** Manifests are serialised with sorted keys and no trailing whitespace. This ensures the manifest hash is stable regardless of field insertion order.

### Feature 5: Named References (Tags)

Tags are mutable, human-readable pointers to manifest hashes. They provide stable names for promoted builds (`production`, `staging`, `canary`) without requiring callers to track manifest hashes.

- **Operator Story (Tag a Release):** "As a deploy operator promoting a build, I need to point the `production` tag to a new manifest hash atomically, so that the next pull of `production` gets the new build without any window where the tag is absent or points to neither the old nor the new manifest."
- **Operator Story (Retrieve by Tag):** "As a build system or deploy system, I need to resolve a tag name to a manifest hash, so that I can retrieve the manifest without knowing its hash in advance."
- **Operator Story (List Tags):** "As a platform engineer, I need to list all current tags and the manifest hash each points to, so that I can audit which builds are currently promoted and to which environments."
- **Operator Story (Delete Tag):** "As a deploy operator retiring an environment, I need to delete a tag, so that the store's reference set reflects the current active set of promotions."

**Feature Details:**
- `create_tag(name: &str, manifest_hash: &ContentHash) -> Result<()>`: Writes `refs/tags/{name}` atomically (tmp + rename). Fails if the manifest hash does not exist in the store — tags must point to real manifests.
- `update_tag(name: &str, manifest_hash: &ContentHash) -> Result<()>`: Same as create; overwrites. Also validates manifest existence.
- `get_tag(name: &str) -> Result<ContentHash>`: Reads `refs/tags/{name}`, returns the manifest hash. Returns `StoreError::NotFound` if the tag doesn't exist.
- `list_tags() -> Result<Vec<(String, ContentHash)>>`: Scans `refs/tags/`, reads each file, returns name + hash pairs.
- `delete_tag(name: &str) -> Result<()>`: Removes `refs/tags/{name}`. Does not affect the manifest or any layers.
- Tag names must match `[a-z0-9][a-z0-9._-]*` — validated on write, not on read.

### Feature 6: Content Integrity & Immutability Enforcement

The store enforces the immutability contract at write time and surfaces corruption through an explicit scan command. Per-pull verification is the **consumer's responsibility** — the store streams bytes, and the consumer (Microvisor or build system) verifies the output hash after decompression.

- **Operator Story (Publish Integrity):** "As a build operator, I need the store to hash incoming bytes during `publish_layer` and reject any write where the computed hash conflicts with an existing blob, so that the store never silently holds a tampered artifact."
- **Operator Story (Immutable Blobs):** "As a security engineer, I need the store to reject any attempt to overwrite an existing blob with different content, so that the content-address guarantee is enforced at the API level and cannot be violated by a buggy or malicious caller."
- **Operator Story (Store Self-Check):** "As an infrastructure operator, I need to run a full integrity scan of the store — re-hashing all blobs against their stored paths — so that I can detect silent disk corruption before it reaches a deploy."
- **Operator Story (Consumer Verification):** "As a deploy operator, I need Microvisor to verify the output hash of every layer it pulls after decompression and before writing to the thin volume, so that a corrupted artifact in the store is caught before it reaches a running VM."

**Feature Details:**
- **Write-time verification:** `publish_layer` hashes the incoming deploy artifact stream as it writes to `tmp/`. On completion, if the computed hash matches a blob that already exists with different content, `StoreError::HashCollision` is returned and the tmp file is discarded. If no collision, the tmp file is renamed into place.
- **Collision semantics:** A hash collision is a fatal store integrity error. The store surfaces it; it does not attempt to resolve it.
- **Verification scan:** `verify_store() -> Result<VerificationReport>`: Iterates all blobs in `objects/` (both deploy and build-cache artifacts), recomputes each hash, checks it matches the file path. Returns a structured report: list of valid blobs, list of failed blobs (path + expected hash + actual hash). Does not delete — callers decide remediation.
- **Consumer-side pull verification:** The store does not verify hashes inline during `pull_layer` — it streams bytes. Consumers verify integrity themselves:
    - **Microvisor (deploy path):** Decompresses the ext4.zst stream, computes SHA-256 of the raw ext4 bytes, compares against the `content_hash` (output hash) from the release manifest. Mismatch → reject the layer, do not write to thin volume.
    - **Build system (cache injection path):** Pulls the OCI build-cache artifact. Integrity is implicitly verified by BuildKit's content-addressable layer model — if the injected layer is corrupt, the build will fail or produce a different output hash.
- **SHA-256 is the hashing algorithm at POC.** `ContentHash` and `InputHash` are both newtypes over `[u8; 32]`. Display format is lowercase hex. They are distinct types to prevent accidentally using an input hash where a content hash is expected (or vice versa).

### Feature 7: Garbage Collection

Layers not referenced by any published manifest are candidates for deletion. GC is the only mechanism for reclaiming storage from the store.

- **Operator Story (Identify Candidates):** "As a build operator, I need to list all layers in the store that are not referenced by any release manifest, so that I understand what would be deleted before I commit to deletion."
- **Operator Story (Dry-Run GC):** "As an infrastructure operator, I need to run GC in dry-run mode and see exactly which blobs would be deleted and how much space would be reclaimed, so that I can confirm the GC is safe before running it destructively."
- **Operator Story (Execute GC):** "As an infrastructure operator, I need to delete all unreferenced blobs from the store so that disk space is reclaimed."
- **Operator Story (Retained References):** "As a build operator, I need tagged manifests to protect all layers they reference from GC, so that a promoted build is never garbage collected while its tag exists."

**Feature Details:**
- **Mark phase:** Walk all manifests in `manifests/` (including those pointed to by any tag in `refs/tags/`). Collect the set of all referenced content hashes. This is the live set.
- **Sweep phase:** Walk all blobs in `objects/`. Any blob whose hash is not in the live set is a GC candidate.
- `gc_candidates() -> Result<GcReport>`: Returns the candidate set with per-blob size (both formats), total reclaimable bytes, and total blob count. Does not delete.
- `gc_execute(report: &GcReport) -> Result<GcSummary>`: Deletes both artifacts (deploy + build-cache) for each candidate, plus the layer metadata in `meta/layers/` and any input hash index entries pointing to the deleted content hash. Returns count and bytes deleted.
- **Safety:** GC never deletes manifests or tags. Only blobs, layer metadata, and orphaned index entries. Manifests themselves are small; there is no GC for manifests at POC. **Trigger:** when manifest count causes `list_builds` scans to exceed 100 ms.
- **Manual trigger only at POC.** No background thread. **Trigger to automate:** store size exceeds a configurable threshold (default suggestion: 50 GB) or manual GC becomes operationally impractical.

## 4. Open Design Questions (To Be Resolved Before Implementation)

### Q1: LocalJsonBackend vs. LocalSQLiteBackend
**Resolved for POC:** Ship `LocalJsonBackend` — flat JSON files for all metadata, no external dependencies. `LocalSQLiteBackend` is a planned second implementation of the same `StorageBackend` trait, triggered when `LocalJsonBackend`'s `list_builds` scan time exceeds 100 ms.

These are two distinct named implementations — not one backend that evolves. `LocalJsonBackend` is not deprecated when `LocalSQLiteBackend` arrives; operators can choose. The `StorageBackend` trait does not change for either. The switch is a one-line construction change in the binary.

**LocalJsonBackend:** Flat JSON files in `meta/builds/`. `list_builds` scans and filters in-process. Correct up to ~1,000 builds.

**LocalSQLiteBackend:** SQLite index in `meta/index.db`. Flat JSON files remain the source of truth; SQLite is the query layer. `list_builds` queries the index. Fast at any scale. Adds write complexity (JSON write + index update; if index update fails, rebuild from JSON scan).

### Q2: Streaming — Resolved
**Resolved:** `pull_layer` returns a streaming `AsyncRead`. `publish_layer` consumes a streaming `AsyncRead`.

Layers are zstd-compressed ext4 blobs that Microvisor streams directly to dm-thin at deploy time. Materialising a full layer in memory is not viable at layer sizes of 200 MB–1 GB+. The `StorageBackend` trait's `get_blob` and `put_blob` are streaming from the start; retrofitting this later would require changing the trait and all implementations simultaneously.

### Q3: Build ID Format
**Decision needed:** Build IDs appear in catalog entries, API responses, and on-disk paths. Options: (a) UUID v4 (random, universally unique, no ordering), (b) timestamp-prefixed UUID (`20260521T143022-{uuid4}`), (c) content hash of the manifest (deterministic, enables deduplication of identical builds).

**Current leaning:** Option (b) — timestamp-prefixed UUID. Human-sortable, globally unique without coordination, debuggable in directory listings. Option (c) complicates the publish flow (manifest hash isn't known until publish completes, creating a circular reference for the catalog entry's own ID).

## 5. Out of Scope (With Re-evaluation Triggers)

| Item | Trigger to Revisit |
|---|---|
| Remote storage backend (S3, GCS, NAS) | Builds run on more than one machine, or Microvisor nodes need to pull layers from a shared store. The `StorageBackend` trait is the insertion point. |
| Network API transport (gRPC, HTTP) | CLI or Microvisor runs on a different machine than the store. `LayerStore` is wrapped in a server; no internal changes. |
| Replication / high availability | Store becomes a single point of failure for the deploy path. |
| Automated GC | Store exceeds 50 GB or GC becomes operationally impractical to run manually. |
| Manifest GC | `list_builds` scan time exceeds 100 ms due to manifest volume. |
| Cryptographic manifest signing | Releases consumed by hosts the build operator doesn't directly control, or compliance mandates signed artifacts. |
| Layer-level file diff (within a blob) | Manifest-level diff insufficient for triage — operators regularly need file-level change detail within a layer. |
| Multi-writer coordination (distributed locking) | More than one build host writes to the same store simultaneously. Current atomicity model (`rename`) is safe for concurrent writers on the same machine; distributed writes require a coordination layer. |
| Authentication / authorisation on the store | Store is accessed by callers the build operator doesn't control. Currently scoped to trusted single-machine use. |
