# Technical Architecture Document (TAD): fs-storage (Layer Store)

This document maps the requirements from `001-prd.md` to concrete Rust types, on-disk structures, and internal component boundaries. It is the authoritative implementation reference for the `fs-storage` crate.

---

## 1. Architecture Overview

`fs-storage` is a two-layer system. The lower layer is a pluggable storage backend (`StorageBackend` trait) that knows only about raw bytes and string-keyed metadata. The upper layer is a typed, layer-aware API (`LayerStore`) that knows about content hashes, input hashes, artifact formats, manifests, tags, and GC. Neither layer knows about the other's implementation details.

```
┌─────────────────────────────────────────────────────────┐
│                      Callers                            │
│          (build system, Microvisor, CLI tools)          │
└────────────────────────┬────────────────────────────────┘
                         │ typed API
┌────────────────────────▼────────────────────────────────┐
│                     LayerStore                          │
│  publish_layer / pull_layer / resolve_input_hash        │
│  publish_manifest / list_builds / get_manifest          │
│  create_tag / get_tag / list_tags                       │
│  verify_store / gc_candidates / gc_execute              │
└────────────────────────┬────────────────────────────────┘
                         │ StorageBackend trait
┌────────────────────────▼────────────────────────────────┐
│               LocalJsonBackend  (POC)                   │
│     flat files, atomic rename, streaming I/O            │
└─────────────────────────────────────────────────────────┘
```

No caller above `StorageBackend` may reference a filesystem path, S3 URL, or any backend-specific primitive. The trait is the only coupling point.

## 2. Type System

### 2.1 Two Hash Spaces

The store tracks two distinct hash spaces that must not be confused. They are separate newtypes over `[u8; 32]` — the compiler prevents accidental substitution.

```rust
/// Output hash: SHA-256 of the raw (uncompressed) ext4 artifact bytes.
/// Computed by the build system during the CONVERT step, before compression.
/// Permanent identity of a layer. Passed to the store via LayerMeta.
/// The store uses it as the blob storage key but cannot independently verify it —
/// it trusts the caller. Consumers (Microvisor, build system) verify after decompression.
pub struct ContentHash([u8; 32]);

/// Input hash: computed by the build system from the stage definition
/// and parent layer hash. Cache-lookup key. Does not address any blob directly.
pub struct InputHash([u8; 32]);
```

Both display as lowercase hex. `ContentHash` is used as the blob storage key and as the cross-manifest reference. `InputHash` is used only in the index lookup path.

The separation matters: the build system queries the store with an `InputHash` to determine whether it needs to build a stage. If the input hash resolves to a `ContentHash`, the stage output already exists and building is skipped. The `ContentHash` then drives all subsequent blob operations.

**The store trusts the caller's content hash.** The content hash is the SHA-256 of uncompressed ext4 bytes, but the store receives and stores compressed blobs. The store cannot independently verify the content hash without decompressing (which would require format-specific knowledge, violating blob opacity). Instead, the store tracks a separate **file checksum** (SHA-256 of the compressed blob bytes as stored on disk) for at-rest corruption detection via `verify_store`. Content-level verification is the consumer's responsibility — Microvisor verifies the content hash after decompression, before writing to the thin volume.

### 2.2 ArtifactFormat

Each layer is stored in two formats under the same `ContentHash`:

```rust
pub enum ArtifactFormat {
    /// Zstd-compressed ext4 image. Consumed by Microvisor → dm-thin.
    Deploy,
    /// Zstd-compressed OCI tar. Consumed by BuildKit cache injection.
    BuildCache,
}
```

The format is encoded as a filename suffix on disk (`.ext4.zst`, `.oci.tar.zst`). The `ContentHash` is derived from the uncompressed ext4 bytes by the build system (the deploy artifact is the source of truth for the hash). The build-cache artifact is stored under the same content hash as a sibling. The store also records a **file checksum** per blob (SHA-256 of the compressed bytes on disk) for at-rest integrity verification — this is separate from the content hash.

## 3. StorageBackend Trait

### 3.1 Definition

```rust
#[async_trait]
pub trait StorageBackend: Send + Sync {
    // Blob operations — format-aware, content-hash addressed
    async fn has_blob(&self, hash: &ContentHash, format: ArtifactFormat) -> Result<bool, StoreError>;
    async fn put_blob(&self, hash: &ContentHash, format: ArtifactFormat, reader: &mut (dyn AsyncRead + Send + Unpin)) -> Result<(), StoreError>;
    async fn get_blob(&self, hash: &ContentHash, format: ArtifactFormat) -> Result<Box<dyn AsyncRead + Send + Unpin>, StoreError>;
    async fn delete_blob(&self, hash: &ContentHash, format: ArtifactFormat) -> Result<(), StoreError>;

    // Metadata operations — string-keyed, opaque bytes
    async fn put_meta(&self, key: &str, value: &[u8]) -> Result<(), StoreError>;
    async fn get_meta(&self, key: &str) -> Result<Option<Vec<u8>>, StoreError>;
    async fn list_meta(&self, prefix: &str) -> Result<Vec<String>, StoreError>;
    async fn delete_meta(&self, key: &str) -> Result<(), StoreError>;
}
```

### 3.2 Object Safety

`get_blob` returns `Box<dyn AsyncRead + Send + Unpin>` rather than `impl AsyncRead` to preserve object safety — `LayerStore` holds the backend as `Arc<dyn StorageBackend>`. `put_blob` takes a `&mut (dyn AsyncRead + Send + Unpin)` for the same reason. The `async_trait` macro erases the async boundary via `Pin<Box<dyn Future>>`.

### 3.3 Atomicity and Durability Contracts

The trait makes no atomicity guarantees beyond what each implementation documents. `LocalJsonBackend` provides POSIX rename atomicity. A future `S3Backend` would document eventual consistency. Callers may not assume stronger guarantees than the implementation documents.

### 3.4 InMemoryBackend

A test-only implementation backed by `Arc<RwLock<HashMap<(ContentHash, ArtifactFormat), Vec<u8>>>>` and a corresponding metadata map. Lives in `src/backends/memory.rs` behind `#[cfg(test)]`. All unit tests for `LayerStore` use `InMemoryBackend` — no filesystem I/O.

## 4. LocalJsonBackend

### 4.1 On-Disk Layout

```
{store-root}/
  objects/
    {sha256[0:2]}/
      {sha256[2:]}.ext4.zst      ← deploy artifact (zstd-compressed ext4)
      {sha256[2:]}.oci.tar.zst   ← build-cache artifact (zstd-compressed OCI tar)
  manifests/
    {manifest-hash}.json         ← full release manifest
  meta/
    layers/
      {content-hash}.json        ← per-layer provenance (LayerMeta)
    index/
      {input-hash}               ← plain text: content hash (no trailing newline)
    builds/
      {build-id}.json            ← BuildCatalogEntry
  refs/
    tags/
      {tag-name}                 ← plain text: manifest hash (no trailing newline)
  tmp/
    {uuid}                       ← staging area for in-progress writes
```

The two-character prefix split under `objects/` mirrors git's object store — directory entry counts stay manageable at scale (256 prefix directories cap at ~400 entries each for a 100,000-layer store).

### 4.2 Atomicity: tmp + rename

All writes — blobs and metadata — follow the same protocol:

1. Write to `tmp/{uuid}` (a fresh UUID per write operation)
2. `fsync` the tmp file
3. `rename(tmp/{uuid}, final_path)` — atomic on POSIX within the same filesystem

Two concurrent writers targeting the same final path both write to distinct `tmp/` files. One wins the rename; the other finds the target already exists and discards its tmp file. The result is identical either way. No file locking is needed.

On `LocalJsonBackend::open()`, the `tmp/` directory is scanned and all files found there are deleted unconditionally — they are incomplete writes from a previously crashed process.

### 4.3 Deduplication

`put_blob` checks the final path before writing:

```
if final_path.exists() → skip write, discard reader, return Ok(())
```

No hash recomputation, no copy. The existence of the file at the content-addressed path is proof of identity.

### 4.4 Directory Creation

`objects/{prefix}/` directories are created on first use via `tokio::fs::create_dir_all`. Concurrent writers racing to create the same prefix directory treat `ErrorKind::AlreadyExists` as success.

### 4.5 Metadata Key → Path Mapping

The metadata key namespace uses `/` as a path separator. The backend maps keys directly to paths under `{store-root}/meta/`:

- `layers/{content-hash}` → `meta/layers/{content-hash}.json`
- `index/{input-hash}` → `meta/index/{input-hash}`
- `builds/{build-id}` → `meta/builds/{build-id}.json`

`list_meta(prefix)` scans the corresponding directory and returns matching keys. Filename extensions are stripped when returning keys (callers work with logical keys, not filenames).

## 5. LayerStore

`LayerStore` holds an `Arc<dyn StorageBackend>` and adds all layer-level semantics above the raw byte boundary.

```rust
pub struct LayerStore {
    backend: Arc<dyn StorageBackend>,
}

impl LayerStore {
    pub fn new(backend: Arc<dyn StorageBackend>) -> Self;
    pub async fn open_local(root: &Path) -> Result<Self, StoreError>;
}
```

`open_local` constructs a `LocalJsonBackend`, creates the required directory tree if absent, runs `tmp/` cleanup, and wraps the backend in `LayerStore`.

### 5.1 Input Hash Index

```rust
/// Returns the content hash for a given input hash, or None if not yet published.
/// This is the cache-hit lookup: < 5 ms target.
pub async fn resolve_input_hash(&self, input_hash: &InputHash) -> Result<Option<ContentHash>, StoreError>;

/// Writes input_hash → content_hash to meta/index/. Called during publish_layer.
/// Idempotent if the mapping is identical. If the mapping conflicts (same input hash,
/// different content hash), the new mapping overwrites — non-deterministic builds are
/// permitted; both hashes appear in LayerMeta for auditability.
async fn register_input_hash(&self, input_hash: &InputHash, content_hash: &ContentHash) -> Result<(), StoreError>;
```

The index file contains the lowercase hex content hash with no trailing newline. `resolve_input_hash` is a single metadata read — no blob I/O.

### 5.2 Blob Operations

```rust
/// Checks for the deploy artifact blob. Both artifacts are published together,
/// so checking one is sufficient. Single has_blob call; < 5 ms target.
pub async fn has_layer(&self, content_hash: &ContentHash) -> Result<bool, StoreError>;

/// Streams both artifacts into the store. Computes file checksums (SHA-256 of
/// compressed bytes) inline during the write for at-rest integrity tracking.
///
/// The content hash (SHA-256 of uncompressed ext4) is provided by the caller
/// in LayerMeta — the store trusts it and uses it as the blob storage key.
/// Content-level verification is the consumer's responsibility.
///
/// On completion:
/// - If blobs already exist at the content hash path (idempotent case): skips write, returns Ok
/// - On success: writes both blobs, records file checksums in LayerMeta,
///   writes layer provenance metadata, and registers the input hash index entry
pub async fn publish_layer(
    &self,
    deploy_reader: &mut (dyn AsyncRead + Send + Unpin),
    cache_reader: &mut (dyn AsyncRead + Send + Unpin),
    meta: LayerMeta,
) -> Result<ContentHash, StoreError>;

/// Returns a streaming reader over the requested format's blob.
/// No full materialisation in memory. First-byte latency < 10 ms target.
/// The caller consumes the stream and verifies integrity (see §7).
pub async fn pull_layer(
    &self,
    content_hash: &ContentHash,
    format: ArtifactFormat,
) -> Result<Box<dyn AsyncRead + Send + Unpin>, StoreError>;
```

**Deduplication in `publish_layer`:** Before writing, the store checks whether blobs already exist at the content hash path. If they do, the write is skipped entirely — this is the idempotent case. The content hash is caller-provided (from `LayerMeta`); the store trusts it as the storage key. The store does **not** independently verify the content hash against uncompressed bytes — that would require format-specific decompression, violating blob opacity. Instead, the store computes file checksums (SHA-256 of the compressed bytes as written to disk) and records them in `LayerMeta.file_checksum_deploy` and `LayerMeta.file_checksum_cache`. These checksums power `verify_store` for at-rest corruption detection.

### 5.3 Manifest & Build Catalog

```rust
/// Serialises to canonical JSON (BTreeMap key ordering, no trailing whitespace),
/// computes manifest hash, stores under manifests/{hash}.json, writes BuildCatalogEntry.
/// Idempotent.
pub async fn publish_manifest(&self, manifest: ReleaseManifest) -> Result<ContentHash, StoreError>;

pub async fn get_manifest(&self, hash: &ContentHash) -> Result<ReleaseManifest, StoreError>;

/// Scans meta/builds/, deserialises all entries, filters in-process, sorts by
/// build_timestamp descending. All filter fields use AND semantics.
/// Trigger to migrate to LocalSQLiteBackend: scan time exceeds 100 ms.
pub async fn list_builds(&self, filter: BuildFilter) -> Result<Vec<BuildCatalogEntry>, StoreError>;

pub async fn get_build(&self, build_id: &BuildId) -> Result<BuildCatalogEntry, StoreError>;
```

**Canonical JSON:** Manifests are serialised via `serde_json` using structs that derive `Serialize` with `BTreeMap`-ordered fields (or by serialising to `serde_json::Value` and re-serialising via a `BTreeMap`). This ensures the manifest hash is stable regardless of field insertion order across Rust versions or platforms.

**`BuildId`** is UUID v4 (random). Catalog entries are sorted by `build_timestamp` for display ordering — the ID carries no ordering information.

### 5.4 Named References (Tags)

```rust
pub async fn create_tag(&self, name: &str, manifest_hash: &ContentHash) -> Result<(), StoreError>;
pub async fn update_tag(&self, name: &str, manifest_hash: &ContentHash) -> Result<(), StoreError>;
pub async fn get_tag(&self, name: &str) -> Result<ContentHash, StoreError>;
pub async fn list_tags(&self) -> Result<Vec<(String, ContentHash)>, StoreError>;
pub async fn delete_tag(&self, name: &str) -> Result<(), StoreError>;
```

Tag names must match `[a-z0-9][a-z0-9._-]*`. Validated on write; not validated on read (the store may contain legacy files that predate the rule).

`create_tag` and `update_tag` are identical operations — both validate the manifest exists in the store before writing, then atomically write the manifest hash to `refs/tags/{name}` via tmp + rename. An absent manifest → `StoreError::NotFound`.

Tag files contain the lowercase hex manifest hash with no trailing newline. `list_tags` scans `refs/tags/`, reads each file, and returns `(name, hash)` pairs.

## 6. Content Integrity

### 6.1 Write-Time Verification

`publish_layer` computes the content hash inline as it writes the deploy artifact to `tmp/`. The hash adaptor wraps the uncompressed byte stream — the `ContentHash` is always derived from raw ext4 bytes, not the compressed form. On stream completion, the computed hash is compared against `meta.content_hash`. Mismatch → `StoreError::HashCollision`, tmp files discarded.

### 6.2 Store Verification Scan

```rust
pub struct VerificationReport {
    pub valid: Vec<ContentHash>,
    pub corrupt: Vec<CorruptEntry>,
}

pub struct CorruptEntry {
    pub path: PathBuf,
    pub expected_hash: ContentHash,
    pub actual_hash: ContentHash,
}

/// Re-hashes all blobs in objects/ (both formats) against their path-derived expected hashes.
/// Does not delete. Callers decide remediation.
pub async fn verify_store(&self) -> Result<VerificationReport, StoreError>;
```

`verify_store` iterates `objects/` recursively, parses the content hash from each filename, recomputes SHA-256 of the file's bytes, and compares. Both artifact formats are checked independently.

### 6.3 Consumer-Side Pull Verification

The store does not verify hashes inline during `pull_layer` — it streams bytes and the consumer is responsible for integrity:

- **Microvisor (deploy path):** Decompresses the `ext4.zst` stream, computes SHA-256 of the raw ext4 bytes, compares against the `content_hash` from the release manifest. Mismatch → reject the layer, do not write to the thin volume.
- **Build system (cache injection):** Pulls `oci.tar.zst`. BuildKit's content-addressable layer model implicitly validates — a corrupt layer produces a different output hash, surfacing the corruption on the next build.

This model was chosen because streaming bytes directly to dm-thin means corruption detected at end-of-stream cannot be rolled back without either buffering the full artifact (defeats streaming) or a dm-thin snapshot invalidation protocol. The consumer has the context to handle the failure correctly; the store does not.

## 7. Garbage Collection

### 7.1 Mark Phase

Walk all manifests in `manifests/` plus all manifests pointed to by tags in `refs/tags/`. Collect all `ContentHash` values from every `layers` array. This is the live set.

Tags are resolved first to avoid a race where a manifest is written between the tag scan and the manifest scan — the GC is conservative: anything reachable via any tag or direct manifest reference is retained.

### 7.2 Sweep Phase

Walk all blobs in `objects/` (both `.ext4.zst` and `.oci.tar.zst` files). Parse the `ContentHash` from the filename. Any hash not in the live set is a GC candidate.

```rust
pub struct GcReport {
    pub candidates: Vec<GcCandidate>,
    pub total_reclaimable_bytes: u64,
}

pub struct GcCandidate {
    pub content_hash: ContentHash,
    pub size_deploy_bytes: u64,
    pub size_cache_bytes: u64,
}

pub struct GcSummary {
    pub deleted_blobs: u64,
    pub deleted_bytes: u64,
}

/// Dry-run. Returns candidates without deleting. < 5 s for 10,000 layers.
pub async fn gc_candidates(&self) -> Result<GcReport, StoreError>;

/// Destructive. Deletes both artifact blobs, the layer provenance metadata
/// (meta/layers/{hash}.json), and any input hash index entries pointing to
/// the deleted content hash (meta/index/ entries whose file contents match
/// the candidate hash).
pub async fn gc_execute(&self, report: &GcReport) -> Result<GcSummary, StoreError>;
```

GC never touches `manifests/` or `refs/tags/`. Manual trigger only at POC — no background thread. Automation trigger: store exceeds 50 GB or manual GC becomes operationally impractical.

## 9. Performance Targets

| Operation | Mechanism | Target |
|---|---|---|
| `resolve_input_hash` | single metadata read (`meta/index/`) | < 5 ms |
| `has_layer` | single `stat` call via `has_blob` | < 5 ms |
| `pull_layer` (first byte) | open + first read from `objects/` | < 10 ms |
| `publish_layer` (non-I/O overhead) | hash adaptor, two renames, two meta writes | < 1 s |
| `get_manifest` / `publish_manifest` | single JSON read/write | < 100 ms |
| `list_builds` | directory scan + in-process filter | < 100 ms |
| `create_tag` / `get_tag` | single file write/read | < 10 ms |
| `gc_candidates` (10,000 layers) | directory walk + live set construction | < 5 s |

`list_builds` at > 100 ms is the trigger to introduce `LocalSQLiteBackend` as a second `StorageBackend` implementation. The `StorageBackend` trait and `LayerStore` do not change; only the backend constructed at startup changes.
