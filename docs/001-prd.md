# Product Requirements Document (PRD): Microvisor Control Plane

## 1. Product Objective
To provide a bare-metal, high-density orchestration control plane that treats standard Linux hosts as programmable hardware multiplexers. The Microvisor must deliver hardware-enforced isolation, low-latency VM lifecycle operations, and transparent observability, completely avoiding heavy host-level daemons or shared state.

**Concrete latency targets** (subject to revision once benched):
- p99 cold boot (spawn-request → first guest instruction): **< 200 ms**
- Snapshot resume (paused → running): **< 10 ms**
- vCPU `KVM_RUN` re-entry after VM-exit: **< 5 µs**
- eBPF NAT per-packet overhead at 64-byte packets: **< 200 ns**

## 2. Target Audience
**Cluster Operators & Platform Engineers:** Individuals responsible for managing fleet nodes, diagnosing system-level latency, and ensuring strict multi-tenant isolation. They need deterministic behavior, zero magic, and native observability.

---

## 3. Core Features & Operator Stories

### Feature 0: Low-Level System Internals (The Orchestration Framework)
Before we launch a VM, the operator needs a predictable, reliable interface to interact with the host node.

*   **Operator User Story (Deployment):** "As a cluster operator, I need the Microvisor to be distributed as a single, statically compiled binary with zero external runtime dependencies (no Docker, no JVM), so that host provisioning is atomic and instant."
*   **Operator User Story (Topology):** "As a platform engineer, I need a strict 1:1 mapping where one guest VM is exactly one host process, so that I can map isolation boundaries transparently."
*   **Operator User Story (Reliability):** "As an SRE, I need the orchestrator to never block the main event loop, so that a slow disk read on one tenant doesn't delay the API response for another tenant."
*   **Feature Details:**
    *   **CLI & Configuration:** Configurable via strict JSON/TOML schemas.
    *   **Runtime:** Built on `tokio` for async/await, ensuring responsive orchestration loops.
    *   **Modular Architecture:** Clean separation of concerns (`storage`, `network`, `cgroup`, `state`), making it extensible for future requirements.

### Feature 1: Tier-0 System Workloads (Dogfooding)
The orchestrator must be capable of running its own dependencies as managed microVMs, keeping the host completely clean.

*   **Operator User Story (Host Purity):** "As a security operator, I want all system services (like tracing aggregators) to run inside isolated microVMs rather than as host processes, so that a compromised or memory-leaking agent cannot impact the host node's stability."
*   **Operator User Story (Deterministic Infrastructure):** "As a cluster operator, I need the control plane to automatically bootstrap these system VMs before accepting user workloads, ensuring telemetry is online from the very first user request."
*   **Feature Details:**
    *   **Boot Sequencing:** The state machine automatically provisions predefined system `VmConfig` profiles on startup.
    *   **Static IPAM:** System VMs are assigned deterministic IPs, allowing the Rust control plane to hardcode telemetry export destinations without service discovery overhead.

### Feature 2: Hardware-Enforced Process Isolation (Compute Fencing)
*Aligns with: Constraint-001, Constraint-005*

*   **Operator User Story (Noisy Neighbor Protection):** "As a platform operator, I need absolute guarantees that a workload's vCPUs are pinned to specific physical cores, so that one tenant running a CPU-intensive task cannot cause context-switch latency for another."
*   **Operator User Story (Flexible Sizing):** "As a workload provider, I need to dynamically configure the memory ceiling and core count per VM request, allowing me to serve both lightweight functions and heavy browser tasks."
*   **Operator User Story (Memory Initialization Choice):** "As a performance engineer, I need to choose per-VM whether to optimize for the absolute fastest boot time (lazy loading) or zero page-fault latency during execution (eager loading)."
*   **Operator User Story (OOM Protection):** "As an SRE, I need hard memory limits enforced at the kernel level with swap disabled, so that a memory leak inside a guest VM triggers a clean OOM kill of that specific microVM rather than degrading the host."
*   **Feature Details:**
    *   **1:1 Thread Mapping:** If a VM requests N cores, the orchestrator allocates N physical host cores and pins exactly one Firecracker vCPU thread to each physical core using `cpuset.cpus`.
    *   **Memory Ceiling:** `memory.max` is set dynamically per request, and `memory.swap.max` is permanently forced to `0`.

### Feature 3: Zero-Shared-State Networking (eBPF)
*Aligns with: Constraint-000, Constraint-004, ADR-004*

*   **Operator User Story (Tenant Isolation):** "As a network security operator, I need to guarantee that no two VMs can "see" each other via ARP spoofing or broadcast traffic, meaning traditional Linux software bridges cannot be used."
*   **Operator User Story (Line-Rate Performance):** "As a performance engineer, I need packet routing to bypass standard host networking stacks (netfilter/iptables), using zero-copy eBPF data paths to achieve near bare-metal throughput."
*   **Operator User Story (Network Observability):** "As a network SRE, I need transparent packet-level observability (e.g., via eBPF tracepoints) to debug dropped connections or latency issues without having to run packet captures inside the tenant's namespace."
*   **Operator User Story (Deterministic Guest Layout):** "As a workload provider, I want the guest OS network configuration to be identical across every launch (e.g., `169.254.1.2`), so I don't have to run DHCP."
*   **Feature Details:**
    *   **Point-to-Point TAPs:** Every VM gets a dedicated TAP interface. No host bridges.
    *   **eBPF NAT (tc hooks):** The host uses Traffic Control (`tc`) eBPF hooks for transparent 1:1 NAT mapping.

### Feature 4: Ephemeral & Direct Storage (Device Mapper)
*Aligns with: Constraint-002, Constraint-007, ADR-002*

*   **Operator User Story (Clean Slate):** "As a security engineer, I need every VM to boot from an immutable snapshot, ensuring that if a workload is compromised, the payload is completely destroyed upon VM shutdown."
*   **Operator User Story (Stateful Seeding):** "As an application developer using the Microvisor (e.g., for browser automation), I need the ability to optionally seed a new ephemeral VM with existing state (cookies, local storage) retrieved from a persistent backend, allowing for warm session resumes."
*   **Operator User Story (Host Cache Protection):** "As a cluster operator, I need guest I/O to bypass the host page cache (`O_DIRECT`), ensuring host memory is reserved strictly for tenant compute."
*   **Feature Details:**
    *   **Device Mapper Thin Provisioning:** Direct `ioctl` commands create CoW (Copy-on-Write) snapshots from read-only base images.
    *   **Metadata Drives:** Ephemeral `ext4` blocks are attached to pass initialization secrets, tasks, or seeded application state to the VM.

### Feature 5: Transparent Observability (The "Microvisor" Lens)
*Aligns with: Constraint-008, ADR-003, ADR-005, ADR-006*

*   **Operator User Story (Zero-Cost Telemetry):** "As a platform operator, I need to monitor CPU usage, disk I/O, and context switches of a workload from the outside, without installing any agents inside the guest OS."
*   **Operator User Story (Traceability):** "As a developer debugging the orchestrator, I need a single `session_id` that links high-level Rust logic directly to low-level kernel events in my distributed tracing interface."
*   **Operator User Story (Starvation Alerts):** "As an SRE, I need automatic alerts if the control plane's main thread is blocked for more than 1 millisecond by a slow kernel API, ensuring I can catch system degradation before it impacts API latency."
*   **Feature Details:**
    *   **Hardware-Assisted Tracing:** Utilization of KVM tracepoints (`tracepoint:kvm:kvm_exit`) and Performance Monitoring Units (PMU).
    *   **eBPF Correlation:** A shared BPF map that links a host `cgroup_id` to the Rust-generated `session_id`.
    *   **Standardized Export:** Direct streaming of correlated data via standard protocols (OTLP) to the telemetry backend.
