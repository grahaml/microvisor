# Technical Architecture Document (TAD): Microvisor

This document outlines the low-level technical design, system prerequisites, and internal component architecture for the Microvisor orchestration plane. It maps the requirements from the PRD (`000-prd.md`) directly to Linux kernel primitives and the Rust implementation.

---

## 1. System Prerequisites & Hardware Preparation

The Microvisor is designed to treat the Linux kernel as a programmable hardware multiplexer. It requires strict asymmetry between the host execution zones and guest execution zones.

### 1.1 Host Boot Configuration (Preemption Fencing)
To prevent VM-Exits, L1/L2 cache invalidation, and TLB thrashing caused by the host OS migrating vCPU threads, physical cores must be isolated entirely from the host scheduler **and** kept clear of kernel-thread and interrupt traffic.

The host must be booted with GRUB parameters that cover all four sources of jitter (e.g., to reserve cores 0–1 for the host and isolate cores 2–15 for VMs):
```text
isolcpus=2-15 nohz_full=2-15 rcu_nocbs=2-15 irqaffinity=0-1 kthread_cpus=0-1
```

- `isolcpus=` removes cores from the default scheduler's load-balancing.
- `nohz_full=` disables the periodic scheduling-tick on those cores.
- `rcu_nocbs=` offloads RCU callback processing to housekeeping cores.
- `irqaffinity=` keeps device interrupts (NIC, NVMe) off the isolated cores — without this, IRQs land everywhere and shred the latency budget regardless of `isolcpus`.
- `kthread_cpus=` confines kernel worker threads (kworker, ksoftirqd, etc.) to housekeeping cores.

**Modern alternative:** `isolcpus=` is functionally deprecated in favor of cgroups v2 `cpuset.cpus.partition=root`, which lets the orchestrator dynamically create an isolated CPU partition at runtime. On kernels ≥ 5.14 the cgroup path is preferred; the boot-time approach remains valid and is the simplest baseline.

### 1.2 Single Process Topology
Every guest microVM maps 1:1 to a host Linux process. Every guest vCPU maps 1:1 to a host `pthread`.

## 2. Core Control Plane Architecture

The control plane is an asynchronous Rust daemon (`tokio`) that interacts directly with kernel interfaces via system calls and `ioctl` boundaries, avoiding external CLI wrappers.

### 2.1 The Observable State Machine
The core of the orchestrator is an event-driven state machine (`VmStateMachine`) with the following strict lifecycle:
`Pending` -> `ProvisioningStorage` -> `ConfiguringNetwork` -> `InitializingCgroup` -> `LaunchingVMM` -> `Running` -> `Terminating` -> `Destroyed`.

### 2.2 Security Boundaries
1.  **Hardware Layer:** KVM (`/dev/kvm`) ensures memory and CPU isolation.
2.  **Resource Layer:** Host `cgroups v2` and CPU pinning prevent resource starvation.
3.  **OS Layer:** Ephemeral RootFS prevents persistent malware.
4.  **Network Layer:** Zero-shared-state routing ensures default-deny isolation.

## 3. Subsystem Specifications

### 3.1 Compute & Virtualization (`src/vmm/cgroup.rs`)
Before vCPU execution begins, the control plane enforces hardware boundaries:
1.  Creates a dedicated cgroup: `/sys/fs/cgroup/orchestrator/vm-{id}`.
2.  Assigns isolated physical cores via `cpuset.cpus`.
3.  Enforces absolute memory ceilings via `memory.max` and disables swap (`memory.swap.max = 0`).
4.  Optionally pins memory to a local NUMA node (`cpuset.mems`) to avoid Inter-Connect latency penalties.

#### Memory Initialization Strategies
When resuming VMs, the orchestrator handles memory via two modes:
*   **Eager Pre-faulting (`MADV_WILLNEED`):** Forces the host kernel to eager-load the Extended Page Tables (EPT) prior to vCPU activation. Trades initial startup latency (~10ms) for deterministic zero-page-fault runtime.
*   **User-Space Faulting (`userfaultfd`):** Lazily fetches pages over an active UDS asynchronously. Optimizes for sub-millisecond boot times at the cost of runtime jitter.

### 3.2 Storage Subsystem (`src/vmm/storage.rs`)
Storage density is achieved using Device Mapper Thin Provisioning (`dm-thin`), bypassing loop devices to avoid global lock contention.

1.  **Base Image:** A read-only base rootfs block device inside a thin pool.
2.  **Instant Ephemeral Disks:** The Rust plane issues an `ioctl` (`DM_DEV_CREATE`, `DM_TABLE_LOAD`) to `/dev/mapper/control` to provision an instantaneous Copy-on-Write (CoW) thin volume.
3.  **Execution:** Firecracker opens the block device with `O_DIRECT` (which bypasses the host filesystem page cache) and submits requests via `io_uring` (an async, low-syscall-overhead I/O path). These are orthogonal concerns — `O_DIRECT` controls caching, `io_uring` controls the submission interface.
4.  **Metadata Drive:** An orchestrator-generated `metadata.ext4` image injected at boot time via `/dev/vdb` containing ephemeral secrets or state.

### 3.3 Stateless Multi-Tenant Networking (`src/vmm/network.rs`)
No software bridges are used. 

1.  **Guest Layout:** The guest OS is hardcoded with a static dummy layout (IP: `169.254.1.2`).
2.  **IPAM:** The Rust control plane tracks host-routable IP slices in a lock-free global atomic bitset (`AtomicU64`).
3.  **eBPF Layer Injection:** An allocated host-routable IP (e.g., `10.0.1.45`) is written to a dedicated `BPF_MAP_TYPE_ARRAY` tied to the instance's TAP device.
4.  **Stateless Rewrite:** An eBPF `tc_egress` hook intercepts packets, overwrites the source IP, updates Layer 3/4 checksums incrementally (`bpf_l3_csum_replace`), and passes the packet to the host interface.

### 3.4 Kernel-Level Observability (`src/vmm/observability.rs`)
The system correlates high-level `session_id` traces with low-level kernel telemetry.

1.  **Trace Exporter:** Uses `tracing-opentelemetry` to export OTLP/gRPC spans to a managed System MicroVM.
2.  **Syscall Auditing:** The `SyscallAuditor` wraps blocking APIs (e.g., writing to `/sys/fs/cgroup`) and emits warnings if the main tokio thread is blocked for >1ms.
3.  **Hypervisor Exit Auditing:** eBPF / `bpftrace` scripts monitor `tracepoint:kvm:kvm_exit` scoped to the orchestrator cgroup tree, writing the exit frequency per `cgroup_id` back to the telemetry pipeline.
