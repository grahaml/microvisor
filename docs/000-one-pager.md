# Project One-Pager: Firecracker Agent Orchestration Plane

## The Problem
Running autonomous AI agents and headless browsers requires executing untrusted, potentially malicious code (often generated by LLMs). Traditional containerization (like Docker or Kubernetes/k3s) shares the host machine's kernel with the workloads. If an agent exploits a kernel vulnerability, it gains access to the host system and all other agents. 

We need a fully sandboxed, highly secure private runtime that can spin up isolated environments in milliseconds, providing each agent with its own dedicated kernel and filesystem. 

## The Evolution: From `private-agent-runtime` to Firecracker
This project is the natural evolution of our previous work on the `private-agent-runtime`. 
*   **Previous Architecture:** Relied on a local `k3s` cluster to orchestrate agent workloads (like the mobile lab). While k3s is excellent for standard microservices, it falls short on true "Layer 1" multi-tenant security for untrusted AI operations. It also carries significant background resource overhead.
*   **New Architecture:** We are pivoting to **Firecracker microVMs**. Firecracker uses KVM to provide hardware-enforced isolation, giving each agent the security of a full Virtual Machine but with the startup speed (<125ms) and density of a container.

## The Goal: A Rust-Based Orchestration Plane
We are not just manually spinning up a single Firecracker VM. The ultimate objective is to build a **full orchestration plane from scratch using Rust**. 

Instead of relying on Kubernetes, we are building our own "mini-cloud" controller that will:
1.  **Manage the VM Lifecycle:** Fast-booting, snapshotting, and tearing down microVMs dynamically as agent workloads are requested.
2.  **Orchestrate Networking:** Automatically provisioning TAP devices, managing internal bridges, and handling NAT routing so isolated agents can reach necessary external APIs (e.g., Anthropic) without exposing the host network.
3.  **Handle Storage:** Dynamically generating custom RootFS images and securely mounting specific metadata drives (containing API keys and state) to the appropriate VMs.
4.  **Provide an API:** Expose a clean API for the broader system to request an agent runtime, execute tasks, and receive results.

## Next Steps
To achieve this rigorously, we will create detailed specification documents for each subsystem (Networking, Storage/RootFS, VM Lifecycle, and the Rust Orchestrator) before implementing the code.
